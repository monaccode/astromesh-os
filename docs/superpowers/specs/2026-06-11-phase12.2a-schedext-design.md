# §12.2a — sched_ext (cargar un scheduler de CPU custom) — Diseño

> **Estado:** Diseño aprobado en brainstorm (2026-06-11).
> **Tipo:** Sub-proyecto post-Fase 4 (F / §12.2 — el diferencial de kernel). El **más ambicioso/riesgoso**
> de post-4 (R3: talento Rust+eBPF). §12.2 se **descompone** en 12.2a (sched_ext, este doc) y 12.2b
> (GPU broker, diferido — no testeable sin GPU local, va con `sysext-gpu`).
> **Precede:** 4.4d (daemon privilegiado Rust+libbpf-rs — la base R3 de carga de programas BPF), otel/criu
> (patrón de capability gated por credencial), 3.x (self-check fail-closed con marcadores a consola).
> **Habilita:** ADR-3 del decomposition doc — kernel **Debian trixie 6.12+** elegido para `sched_ext` (≥6.12).
> **Alcance elegido (brainstorm):** **cargar un scheduler BPF mínimo conocido (scx_simple)**, gated,
> probar que queda activo y `astromeshd` sigue funcional. **Cero cambios de runtime.** Política
> agent-aware propia → futuro.

---

## 0. Contexto y propiedad objetivo

§12.2 del spec maestro: `sched_ext` scheduler + GPU broker. Se descompone (§0.2). 12.2a entrega la
**capability de scheduler custom**: el OS carga un scheduler de CPU vía sched_ext, el kernel lo reporta
activo, y `astromeshd` sigue sirviendo bajo él. Demuestra que el nodo puede programar su CPU con política
propia (R3) con la red de seguridad del **watchdog de sched_ext** (si el scheduler BPF se cuelga o stalea,
el kernel lo desactiva y revierte a CFS automáticamente).

### 0.1 Realidad del entorno (discovery)

- **ADR-3 eligió el kernel para esto.** El decomposition doc fijó **Debian trixie / kernel 6.12+** para
  habilitar `sched_ext` (≥6.12). La imagen usa `linux-image-cloud-amd64`. **Falta confirmar
  empíricamente `CONFIG_SCHED_CLASS_EXT`** en ese kernel (el primer assert del gate); la base está pensada
  para soportarlo, pero Debian podría no haberlo habilitado — riesgo R-mayor, documentado.
- **Base R3 ya existente.** 4.4d trae un daemon Rust con `libbpf-rs` + el toolchain de build de eBPF
  (clang/libbpf/libbpf-cargo) en CI; `libelf1`/`zlib1g`/`libzstd1` ya se hornean (deps de libbpf). Un
  scheduler scx (BPF struct_ops + loader userspace) reusa ese andamiaje.
- **Reemplazar CFS es invasivo → opt-in.** A diferencia de 12.3 (hardening always-on), cargar un
  scheduler system-wide cambia TODO el scheduling. Va gated por credencial (`sched_ext: true`), default
  off, como otel/criu.
- **scx_simple existe como ejemplo mínimo.** El árbol de sched_ext (`tools/sched_ext` del kernel / repo
  scx) trae `scx_simple` (~scheduler global simple). Apoyarse en él evita escribir un scheduler BPF
  desde cero (la API scx —`select_cpu`/`enqueue`/`dispatch`/`dispatch`— es compleja). Mismo criterio que
  CRIU en 12.7 y systemd-directives en 12.3: el MVP se apoya en tooling existente.

### 0.2 Descomposición de §12.2

| Sub | Pieza | Testeable local | Este doc |
|---|---|---|---|
| **12.2a** | sched_ext scheduler (scx_simple, gated) | ✅ sí (si el kernel soporta CONFIG_SCHED_CLASS_EXT) | ✅ |
| **12.2b** | GPU broker (arbitraje de GPU entre agentes) | ❌ no (sin GPU en las VMs; va con `sysext-gpu` diferido) | → futuro |

## 1. Arquitectura — loader privilegiado gated + self-check (patrón 4.4d + otel/criu)

Gated por `sched_ext: true` (default off). Dos unidades guardadas:

- **`astromesh-schedext.service`** (loader, `Type=exec`, privilegiado, sin hardening): guarda — si el
  `runtime.yaml` activo no tiene `spec.sched_ext.enabled: true`, log + `exit 0`. Si sí: corre el binario
  del scheduler (`/usr/bin/scx_simple`) **en foreground**. Mientras el proceso vive, el scheduler BPF
  está attached al kernel; si muere, el kernel revierte a CFS. Necesita caps plenas (cargar struct_ops
  BPF), por eso no lleva el drop-in de hardening.
- **`astromesh-schedext-check.sh`** + `.service` (oneshot, `After=astromesh-schedext.service`, gated):
  asserta y emite marcadores `[schedext]` a consola, fail-closed (exit ≠ 0 en fallo):
  1. **`SCHEDEXT-SUPPORTED OK`** — existe `/sys/kernel/sched_ext/` (kernel con `CONFIG_SCHED_CLASS_EXT`).
  2. **`SCHEDEXT-ACTIVE OK`** — `/sys/kernel/sched_ext/state` == `enabled` y `/sys/kernel/sched_ext/root/ops`
     muestra el nombre del scheduler (`simple`). (El loader lo activó.)
  3. **`RUNTIME-FUNCTIONAL OK`** — `astromeshd` `/v1/health` 200 bajo el scheduler custom (el sistema
     sigue usable; el watchdog no revirtió por stall).
  4. **`SCHEDEXT GATE OK`**.

  (Nota: el check NO es `Requires=` de astromeshd —no es hardening fail-closed del runtime, es la
  verificación de la capability—; es gated igual que el loader. astromeshd arranca igual; el check valida
  que corre OK bajo el scheduler.)

---

## 2. El binario del scheduler — build-input (patrón otelcol/eBPF)

`scx_simple` (scheduler C mínimo de ejemplo de sched_ext: BPF struct_ops + loader userspace) se **buildea
en el host/CI** con el toolchain de eBPF de 4.4d (clang + libbpf + bpftool + headers de sched_ext) y se
entrega como build-input **`dist/scx_simple`**, horneado **solo** en builds sched_ext (condicional a la
presencia del binario, como `dist/otelcol`). Los demás gates no lo cargan ni pagan tamaño.

Fuente de `scx_simple`: el repo `sched-ext/scx` (o `tools/sched_ext` del kernel). El recipe exacto de
build (vendoring, versión de libbpf, flags de clang/BTF) es un **ítem de iteración** del primer build
(estilo 4.4e), arrancando del andamiaje de build del daemon eBPF de 4.4d.

---

## 3. El gate (`tests/boot/schedext-and-assert.sh`)

1. Bootea **1 VM** con machine-config (SMBIOS, patrón 4.1) sobre perfil estándar **más `sched_ext: true`**
   → `machine-config.sh` fija `spec.sched_ext.enabled: true`. `-nic user,hostfwd` para `/v1`.
2. Espera `/v1/health` 200. Grep consola: `[schedext] SCHEDEXT-SUPPORTED OK`, `SCHEDEXT-ACTIVE OK`,
   `RUNTIME-FUNCTIONAL OK`, `SCHEDEXT GATE PASSED`.

**Negativo/regresión:** boot sin el flag → loader + check no-op → CFS normal → gates previos intactos.

El gate necesita **KVM** (sched_ext + struct_ops BPF no son viables bajo TCG lento) → WSL2+KVM / runner
con nested-virt, no macOS.

## 5. Componentes y aislamiento

- **Loader (privilegiado):** entrada = flag + el binario scx_simple; salida = scheduler BPF attached
  mientras vive. Contrato = "mientras corre, el scheduler custom está activo".
- **Self-check:** entrada = `/sys/kernel/sched_ext/*` + `astromeshd` `/v1/health`; salida = marcadores +
  exit-code. Verifica SUPPORTED/ACTIVE/FUNCTIONAL.
- **scx_simple (build-input):** binario estándar; su contrato es "carga un scheduler sched_ext y lo
  mantiene". Testeable aislado (correrlo y leer `/sys/kernel/sched_ext/state`).
- **machine-config (mod):** entrada = credencial `sched_ext`; salida = `spec.sched_ext.enabled`. Reusa el
  parse de 4.1/4.3/4.4/12.7.
- **astromeshd:** **sin cambios** — corre bajo el scheduler custom, no participa de la orquestación.

## 6. Criterios de done

- Local `dev-loop.sh schedext` → `SCHEDEXT GATE PASSED` (scx_simple activo: `/sys/kernel/sched_ext/state`
  == enabled + astromeshd `/v1/health` 200 bajo él).
- CI `phase4-schedext.yml` verde (build de scx_simple + imagen + gate).
- Gates de Fase 0/1/2/3/4.* siguen verdes (guarda off-by-default; sin flag → CFS normal; `dist/scx_simple`
  ausente en builds no-schedext → no horneado).
- El nodo carga el scheduler custom **solo** cuando `sched_ext.enabled` (default off): cero cambio para
  nodos existentes.
- Roadmap post-4: §12.2a marcado done; §12.2b (GPU broker) registrado como diferido.

## 7. Riesgos (el más alto de post-4 — el gate ES la prueba)

| Riesgo | Mitigación / nota |
|---|---|
| **Kernel sin `CONFIG_SCHED_CLASS_EXT`** | ADR-3 eligió 6.12+ para esto; el check `SCHEDEXT-SUPPORTED` lo confirma en el primer run. Si falta, hay que pinear/configurar un kernel con sched_ext (descubrimiento mayor; documentar y, si necesario, acotar el alcance). |
| **Build de `scx_simple`** (clang/libbpf/bpftool, headers de sched_ext, BTF) | Reusa el toolchain eBPF de 4.4d; build-input condicional como otelcol. El recipe exacto es ítem de iteración del primer build (estilo 4.4e). |
| Cargar struct_ops sched_ext bajo KVM nested | El loader corre privilegiado; el watchdog del kernel revierte a CFS si el scheduler stalea. El gate lo valida; iterar flags/permite si el load falla. |
| scx_simple degrada el sistema bajo carga | Es un scheduler global simple, suficiente para el demo (cargar + activo + astromeshd responde); el watchdog protege. Política seria → futuro. |
| El loader (`Type=exec`) muere → revierte a CFS a mitad del gate | El self-check corre `After=` el loader y verifica `state==enabled` mientras el loader vive; si revirtió, `SCHEDEXT-ACTIVE` falla (correcto). |
| Techo 500MB | `scx_simple` es chico (~cientos de KB); horneado solo en builds schedext. Verificar el gate de tamaño de Fase 1 si se hornea en el build estándar (no se hornea sin el binario staged). |
| Romper gates previos | Guarda por `spec.sched_ext.enabled` off-by-default; sin flag, CFS intacto; binario no horneado en builds no-schedext. |

## 8. Fuera de alcance (futuro)

- **§12.2b GPU broker** — arbitraje de GPU entre agentes; no testeable sin GPU, va con `sysext-gpu`
  (diferido). Sub-proyecto separado.
- **Scheduler agent-aware propio** — un scheduler BPF que priorice el cgroup de agentes / aplique quotas
  de CPU por agente (el diferenciador R3 real, sobre la capability que entrega 12.2a).
- **Integración con 12.3/12.4/PSI** — scheduling reactivo a presión de memoria/egress.
- **Cambios de runtime** — ninguno en 12.2a-MVP.
