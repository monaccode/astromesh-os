# §12.7 — CRIU checkpoint/restore del runtime (round-trip con estado vivo) — Diseño

> **Estado:** Diseño aprobado en brainstorm (2026-06-11).
> **Tipo:** Sub-proyecto post-Fase 4 (F / §12.7 — el diferencial de kernel). Ganancia incremental: la
> pata de **densidad** del marco de validación (confianza · atribución · densidad); confianza y
> atribución ya están (fase 3 + 4.4/4.3b).
> **Precede:** 3.4 (sandbox del runtime — define que astromeshd corre cerrado y que CRIU lo maneja un
> componente privilegiado externo), 4.4d (patrón de daemon privilegiado fuera del sandbox), 4.1
> (machine-config + render de runtime.yaml), 3.x self-checks (patrón de unidad guardada con marcadores).
> **Alcance elegido (brainstorm):** **C/R round-trip del proceso `astromeshd` entero**, prueba =
> **uptime continuo + API funcional** tras restore, **cero cambios de runtime** (OS-puro), 1 VM.

---

## 0. Contexto y propiedad objetivo

§12.7 del spec maestro: snapshot/restore con CRIU. El OS demuestra que puede **checkpointear el proceso
`astromeshd` corriendo y restaurarlo**, conservando su estado en memoria. Es la base de todo lo que CRIU
habilita después (warm-start, migración live, pausa/evacuación por densidad), y por sí mismo prueba la
capacidad de C/R sobre el runtime real.

### 0.1 Realidad del runtime (discovery — define el alcance)

- **Agentes in-process.** Los agentes corren como coroutines Python dentro del **único** proceso
  `astromeshd` (3.4: "in-process (Python), no como subprocesos separados"). → La unidad de CRIU **no
  puede ser "un agente"**; es el **daemon entero**.
- **Mono-proceso uvicorn.** `daemon/core.py` lanza `uvicorn.Server` **sin `workers=`** (un solo proceso,
  un event loop vía `asyncio.run`). → Un solo árbol de proceso para CRIU, sin fork multi-worker.
- **astromeshd está sandboxeado** (3.4): `astromeshd.service` corre bajo seccomp, `RestrictNamespaces=yes`,
  `NoNewPrivileges=yes`, `ProtectControlGroups=yes`. CRIU necesita `CAP_CHECKPOINT_RESTORE`/`CAP_SYS_ADMIN`,
  ptrace-seize, manipular namespaces. → CRIU **no lo puede ejecutar el propio astromeshd**: lo maneja un
  **componente privilegiado externo** (mismo encuadre que el daemon Rust de eBPF de 4.4d, que corre
  privilegiado fuera del sandbox).
- **Discriminador CRIU-vs-restart sin tocar el runtime.** `astromesh/api/routes/system.py` captura
  `_start_time = time.time()` a nivel módulo (al import, = arranque del proceso), y
  `GET /v1/system/status` devuelve `uptime_seconds = time.time() - _start_time`. Es un dato **solo en
  RAM**: CRIU restore conserva `_start_time` (el uptime sigue subiendo continuo); un restart plano lo
  resetea a ~0. → Prueba de identidad de proceso **con cero cambios de runtime**.
- **Por qué no estado de sesión:** los backends de memoria de conversación son sqlite/pg/redis (no hay
  in-memory); persistirían a disco igual, así que "sobrevivir" no probaría CRIU. El uptime sí es
  RAM-only. Supervivencia de sesión en RAM → fuera de alcance (necesitaría backend in-memory, vertical).

Conclusión: §12.7-MVP es **OS-puro** (cero runtime), driveado por una unidad privilegiada.

## 1. Arquitectura — orquestador privilegiado in-VM

Sigue el patrón de los self-checks de fase 3 (sandbox-check, hardening-check): una **unidad oneshot que
se auto-ejecuta en boot** (guardada por flag), corre el ciclo de C/R, e imprime marcadores a consola; el
gate host-side solo bootea y grepea. La unidad **no** lleva el hardening drop-in (necesita caps plenas).

### 1.1 El ciclo sin pelear con systemd

systemd supervisa `astromeshd.service`. Para no provocar un re-arranque que compita con el restore, el
orquestador **no mata** al proceso: lo vuelca vivo, lo para limpio, y restaura.

1. `criu dump --tree <pid> --leave-running --images-dir /var/lib/astromesh/criu …` → vuelca la imagen
   **sin matar** astromeshd (systemd no se entera; el proceso sigue sirviendo).
2. `systemctl stop astromeshd` → parada **limpia** (libera :8000 y el PID). Al ser un stop intencional
   (no un fallo), systemd **no** re-arranca la unidad.
3. `criu restore --images-dir /var/lib/astromesh/criu -d …` → restaura la imagen volcada como proceso
   **detached**, re-bindeando el socket de escucha :8000.

Sin drop-ins condicionales, sin race de `Restart=`. El proceso restaurado corre **fuera** del cgroup/unit
de systemd → limitación MVP documentada (§5); la re-adopción a systemd es futuro.

## 2. Flujo del gate (dentro de la VM, lo ejecuta `astromesh-criu-gate.sh`)

```
guard: si runtime.yaml activo no tiene criu.enabled: true → log "[criu] no es boot criu; skipping" + exit 0
wait /v1/health 200
U1   = GET /v1/system/status .uptime_seconds            # ej. ~25s; dato en RAM (_start_time)
POST /v1/agents/phase0-smoke/run  (stub)                # prueba que sirve PRE-checkpoint
PID  = pid de astromeshd (systemctl show -p MainPID astromeshd.service)
criu dump --tree $PID --leave-running --images-dir /var/lib/astromesh/criu <flags>   → "CRIU-DUMP OK"
systemctl stop astromeshd                               # libera :8000, sin restart
criu restore --images-dir /var/lib/astromesh/criu -d <flags>                         → "CRIU-RESTORE OK"
wait :8000 (timeout)
U2   = GET /v1/system/status .uptime_seconds            # DEBE ser ≈ U1 + wall-elapsed, NO ~0
POST /v1/agents/phase0-smoke/run  (stub)                # API FUNCIONAL post-restore (200/answer)
assert: U2 >= U1  (uptime continuo, identidad de proceso)
        && segunda corrida respondió                    (continuidad funcional)
→ "CRIU C/R GATE PASSED"
```

**Discriminador:** un restart plano daría `uptime_seconds ≈ 0`; CRIU lo conserva continuo. El assert es
`U2 >= U1` (con margen para el wall-time del ciclo). La 2ª corrida prueba que el restore no quedó "a
medias" (el socket :8000 y el event loop volvieron operativos).

**Negativo/regresión:** un boot sin `criu.enabled` → la unidad hace no-op; astromeshd no se toca. Misma
convención de guarda que otel (4.3) / mesh (4.2).

## 4. El gate (`tests/boot/criu-cr-and-assert.sh`)

1. Bootea **1 VM** con machine-config (SMBIOS, patrón 4.1) sobre perfil estándar (p.ej. `worker`) **más
   `criu: true`** en la credencial → `machine-config.sh` fija `criu.enabled: true`. `-nic user,hostfwd`
   para leer `/v1` desde el host.
2. Espera `/v1/health` 200. Asserta que la consola muestra `[criu] CRIU-DUMP OK` y `[criu] CRIU-RESTORE OK`.
3. Asserta `CRIU C/R GATE PASSED` en la consola (el orquestador ya validó uptime continuo + API funcional
   dentro de la VM). Imprime el resultado al host.

El gate host-side es delgado: bootea y grepea (toda la lógica de C/R y los asserts viven en el
orquestador in-VM, como los self-checks de 3.x). El boot necesita KVM (CRIU + el ciclo no son viables bajo
TCG lento) → corre en WSL2+KVM / runner Linux con nested-virt, no en macOS.

## 5. Componentes y aislamiento

- **Orquestador (privilegiado):** entrada = flag `criu.enabled` + el proceso astromeshd corriendo; salida
  = imagen CRIU en `/var/lib/astromesh/criu` + proceso restaurado + marcadores. Testeable como unidad: su
  contrato es la secuencia dump→stop→restore→assert y los marcadores de consola.
- **machine-config (mod):** entrada = credencial SMBIOS `criu`; salida = `criu.enabled` en runtime.yaml.
  Reusa el parse PyYAML de 4.1/4.2/4.3.
- **Gate host-side:** orquesta 1 VM + grep. Independiente de la lógica interna del orquestador.
- **astromeshd:** **sin cambios** — es el sujeto del C/R, no participa de la orquestación.

## 6. Criterios de done

- Local `dev-loop.sh criu` → `CRIU C/R GATE PASSED` (1 VM: dump --leave-running + stop + restore; uptime

- CI `phase4-criu.yml` verde.
- Gates de Fase 0/1/2/3/4.* siguen verdes (unidad guardada por `criu.enabled`, off por default; `criu` en

- El nodo hace C/R **solo** cuando `criu.enabled` (default off): cero cambio para nodos existentes.
- Roadmap post-4: §12.7 marcado done con referencia de run.

## 7. Riesgos

CRIU sobre un daemon Python real es genuinamente difícil; **el gate ES la prueba** y varios flags son
ítems de iteración empírica (estilo ITERATE de 4.4e).

| Riesgo | Mitigación / nota |
|---|---|
| CRIU no puede volcar el daemon Python/uvicorn/asyncio (epoll/eventfd/timerfd, muchos fds, mmaps del venv) | Generalmente soportado por CRIU; el gate lo valida empíricamente. Punto de arranque de flags: `--tcp-established --file-locks --ext-unix-sk --link-remap --shell-job` (no) — iterar hasta dump+restore verde. |
| **Sockets externos**: `sd_notify` AF_UNIX a systemd + stdout/stderr a journald | El dump usa `--ext-unix-sk` (o se cierran antes); tras restore el stdout del proceso restaurado se pierde (era el socket de journald) — **el gate lee uptime por HTTP, no por logs**, así que es aceptable. El sd_notify ya cumplió su función (notify_ready) antes del checkpoint. |
| El socket de escucha :8000 no re-bindea tras restore | `systemctl stop` libera el puerto antes del restore; CRIU restaura sockets de escucha. El `wait :8000` + 2ª corrida lo confirman. Si falla, es señal de un fd externo no manejado → iterar flags. |
| Kernel sin `CONFIG_CHECKPOINT_RESTORE`/CRIU bajo KVM | El kernel Debian de mkosi lo trae habilitado; validar en el primer run del gate. |
| Proceso restaurado **fuera** del cgroup/unit/sandbox de systemd | Limitación MVP documentada (§8). El gate prueba C/R + continuidad funcional, no la re-adopción. Producción: `criu restore` bajo un scope de systemd / `systemd-run` o native checkpoint — diferido. |
| `RestrictNamespaces`/seccomp del sujeto interfieren con el restore | CRIU vuelca y re-aplica el estado seccomp del proceso; el dumper es externo y privilegiado (no sujeto a `NoNewPrivileges` del target). Validar en el gate; si el restore falla por seccomp, documentar y ajustar. |
| Techo 500MB (R4) | `criu` + deps ~5MB; el gate de tamaño de Fase 1 debe seguir verde — verificar. |
| Cambiar comportamiento de gates previos | Guarda por `criu.enabled` (off por default), idéntica a la de otel/mesh; `criu` en Packages es inerte sin el flag. |

## 8. Fuera de alcance (futuro)

- **Re-adopción a systemd** del proceso restaurado (cgroup/unit/sandbox) — el MVP restaura detached.
- **C/R a través de update A/B** (kernel/libs cambian entre slots) — frágil; no MVP.
- **Migración live entre nodos** de la malla (4.2) — C/R + transferencia de la imagen al peer.
- **Pausa/evacuación por densidad** (12.7 fase 2) — integrar C/R con señal de idle/quota para congelar
  nodos idle y liberar RAM.
- **Supervivencia de sesión en RAM** — necesitaría un backend de memoria in-memory (hoy sqlite/pg/redis);
  el MVP prueba identidad de proceso (uptime) + continuidad funcional, no estado de conversación.
- **Cambios de runtime** — ninguno en 12.7-MVP; cualquier afinación del runtime para CRIU-friendliness
  (cerrar fds externos en un hook de checkpoint) es trabajo separado.
