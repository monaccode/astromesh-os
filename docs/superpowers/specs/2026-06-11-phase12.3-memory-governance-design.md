# §12.3 — Gobierno de memoria por cgroup (blast-radius acotado + recuperación definida) — Diseño

> **Estado:** Diseño aprobado en brainstorm (2026-06-11).
> **Tipo:** Sub-proyecto post-Fase 4 (F / §12.3 — el diferencial de kernel). Ganancia incremental; la
> dimensión **memoria** del gobierno de recursos, complementando el control de **egress** (red) de 4.4e.
> **Precede:** 3.4 (sandbox del runtime — patrón de hardening always-on + self-check fail-closed vía
> `Requires=`, que este sub-proyecto reusa 1:1), 3.5 (egress fail-closed), 4.4e (enforcement de quota
> como encuadre del gobierno de recursos).
> **Alcance elegido (brainstorm):** **gobierno de memoria por cgroup, OS-puro** (directivas systemd +
> self-check), **cero cambios de runtime**, 1 VM. Always-on (hardening), no opt-in.

---

## 0. Contexto y propiedad objetivo

§12.3 del spec maestro: mem/OOM con semántica de agente. La propiedad demostrable, dado el modelo real
del runtime (§0.1), es: un agente que fuga o explota memoria queda **acotado al presupuesto de memoria de
su cgroup** — el cgroup-OOM-killer lo contiene al cgroup de `astromeshd` (el host, el OTel collector, el
daemon eBPF, la malla y todo lo demás del nodo sobreviven) y systemd recupera con política definida, en
lugar del OOM-killer del host eligiendo una víctima arbitraria a nivel nodo. "Semántica de agente" = el
blast-radius del workload de agentes está **acotado a su budget de cgroup, con recuperación determinista**.

### 0.1 Realidad del runtime (discovery — define el alcance)

- **Agentes in-process.** Corren como coroutines Python dentro del **único** proceso `astromeshd` (3.4).
  → **No hay proceso por-agente** que el OOM-killer pueda matar selectivamente; "OOM con semántica de
  agente" no puede ser, literalmente, matar un agente puntual.
- **El runtime no tiene control de admisión ni de concurrencia.** No hay semáforo, límite de runs activos,
  gate de admisión, ni manejo de memoria/OOM en `engine.py`/`services.py`. → Cualquier acción "app-side"
  (rechazar runs bajo presión) sería un **cambio vertical** del runtime — fuera de alcance del MVP.
- **`astromeshd.service` no tiene hoy ninguna directiva de memoria** (`MemoryAccounting`/`MemoryMax`/
  `OOMPolicy`/`MemoryHigh`). Solo lleva el hardening de sandbox (3.4, `30-sandbox.conf`) y el egress
  (3.5/3.6). → El gobierno de memoria es terreno nuevo, OS-puro.
- **cgroup v2 + controlador de memoria + PSI disponibles.** cgroup v2 ya está activo (el egress usa
  cgroup-BPF; el sandbox usa `ProtectControlGroups`). El kernel cloud de Debian trae el controlador de
  memoria y PSI habilitados.

Conclusión: §12.3-MVP es **OS-puro, always-on** (hardening de memoria), con la **misma forma que el
sandbox 3.4**: un drop-in en `astromeshd.service` + un self-check fail-closed que `astromeshd` `Requires=`.

## 1. Arquitectura — drop-in always-on + self-check fail-closed (patrón 3.4 sandbox)

### 1.1 Drop-in `50-memory.conf` en `astromeshd.service` (always-on)

```ini
[Unit]
Requires=astromesh-memory-check.service
After=astromesh-memory-check.service

[Service]
MemoryAccounting=yes
# Porcentaje de RAM física → escala con el tamaño de VM. astromeshd usa ~200 MB, ≪ 70/80% (1.4/1.6 GB en
# una VM de 2 GB), así que no afecta workloads normales; solo capea un runaway.
MemoryHigh=70%
MemoryMax=80%
# El swap no debe enmascarar el límite (la imagen no tiene swap, pero explícito por claridad/forward-compat).
MemorySwapMax=0
# Recuperación determinista: si el cgroup-OOM mata al proceso, la unidad se considera fallida y se reinicia.
OOMPolicy=kill
Restart=on-failure
RestartSec=2
```

- **Always-on** (como `30-sandbox.conf` y `40-egress.conf`): es hardening, no una capability opt-in.
- **Fail-closed** vía `Requires=astromesh-memory-check.service`: si el gobierno de memoria no se puede
  aplicar/verificar, `astromeshd` no arranca (ADR-4: el agente no corre sin la protección).
- `MemoryMax`/`MemoryHigh` en **porcentaje** para no romper gates previos de distinto tamaño de VM.

### 1.2 Self-check `astromesh-memory-check.sh` (corre antes de astromeshd, como sandbox-check)

Tres aserciones, marcadores `[memory]` a consola, fail-closed (exit ≠ 0 en cualquier fallo):

1. **`MEMORY-ACCOUNTING OK`** — `systemctl show astromeshd.service -p MemoryAccounting` == `yes`.
2. **`MEMORYMAX-SET OK`** — `systemctl show astromeshd.service -p MemoryMax,OOMPolicy`: `MemoryMax` es un
   valor finito (≠ `infinity`) y `OOMPolicy=kill`. (Lee el valor efectivo que systemd resolvió del `80%`.)
3. **`POSITIVE-OOM OK`** — prueba de contención **atribuible** (análoga al POSITIVE-BLOCK del sandbox):
   ```
   systemd-run --scope -p MemoryMax=64M -p MemorySwapMax=0 --quiet -- \
       /opt/astromesh/venv/bin/python3 -c 'b=bytearray(); [b.extend(bytes(8*1024*1024)) for _ in range(64)]'
   ```
   Un hog que intenta alocar ~512 MB bajo un `MemoryMax=64M` queda **cgroup-OOM-killed dentro de su scope
   transitorio** (contenido) → `systemd-run` retorna no-cero / el scope reporta OOM. El check + el host
   **sobreviven**. Confirma que el kernel enforcea límites de memoria por cgroup — el mismo mecanismo que
   protege a `astromeshd`. Atribuible: bajo un cgroup con `MemoryMax`, la muerte es del cgroup-OOM (no del
   host), distinguible de un `MemoryError` de Python por el SIGKILL (exit 137 / kill) y/o por el contador
   `memory.events:oom_kill` del scope.

El check NO toca el cgroup de astromeshd (el hog vive en un scope transitorio propio), así que no pone en
riesgo al runtime.

## 2. El gate (`tests/boot/memory-oom-and-assert.sh`)

Always-on → no necesita credencial especial; boot estándar de 1 VM (patrón sandbox/hardening):

1. Bootea **1 VM** sobre un perfil estándar (p.ej. `worker`), `-nic user,hostfwd` para `/v1`.
2. Espera `/v1/health` 200 — que astromeshd haya arrancado **prueba** que el memory-check pasó (lo
   `Requires=`; si fallara, astromeshd no arrancaría y `/v1/health` nunca subiría).
3. Grep en consola: `[memory] MEMORY-ACCOUNTING OK`, `MEMORYMAX-SET OK`, `POSITIVE-OOM OK`,
   `MEMORY GATE PASSED`. Imprime el resultado al host.

**Negativo/fail-closed:** si el controlador de memoria no estuviera o el POSITIVE-OOM no contuviera el
hog, el check sale ≠ 0 → `Requires=` rompe → astromeshd no arranca → `/v1/health` nunca sube → gate rojo.

El gate host-side es delgado (boot + grep); toda la lógica vive en el self-check in-VM (patrón 3.x).

## 4. Componentes y aislamiento

- **Drop-in (directivas):** entrada = unit astromeshd; salida = cgroup de astromeshd con accounting +
  `MemoryMax`/`MemoryHigh`/`OOMPolicy`/`Restart`. Declarativo; su contrato es el conjunto de directivas.
- **Self-check (privilegiado, fail-closed):** entrada = el cgroup de astromeshd + el controlador de
  memoria del kernel; salida = marcadores + exit-code (gate `Requires=`). Testeable: corre el POSITIVE-OOM
  y verifica contención.
- **Gate host-side:** boot + grep. Independiente de la lógica del check.
- **astromeshd:** **sin cambios** — es el sujeto protegido, no participa de la verificación.

## 5. Criterios de done

- Local `dev-loop.sh memory` → `MEMORY GATE PASSED` (1 VM: accounting/max/oompolicy presentes +
  POSITIVE-OOM contenido).
- CI `phase4-memory.yml` verde.
- **Todos los gates previos siguen verdes** — always-on: el drop-in `MemoryMax=80%` + `Requires=check` no
  debe romper ningún boot existente (astromeshd RSS ≪ 80%; verificar en CI que boot/update/sandbox/otel/
  mesh/ebpf siguen arrancando astromeshd con el drop-in aplicado).
- El gobierno aplica en **todo** boot (hardening always-on), con recuperación determinista por `Restart=`.
- Roadmap post-4: §12.3 marcado done con referencia de run.

## 6. Riesgos

| Riesgo | Mitigación |
|---|---|
| Always-on `MemoryMax`/`Requires=check` rompe un gate previo | `MemoryMax=80%`/`MemoryHigh=70%` (porcentaje, generoso; astromeshd ~200 MB ≪ 1.6 GB en VM de 2 GB). El POSITIVE-OOM usa un **scope transitorio** low-limit, no toca el cgroup de astromeshd. El gate exige que los gates previos sigan verdes (§5). |
| Controlador de memoria cgroup v2 ausente en el kernel | El kernel cloud de Debian lo trae habilitado (cgroup v2 ya activo por el egress-BPF/sandbox). El check fail-closed lo valida: si no enforcea, el POSITIVE-OOM no contiene → rojo. |
| `systemd-run --scope` no disponible o no aísla la memoria | `systemd-run` es estándar en systemd. El flag exacto (`--scope` vs `--service`, `--wait`, lectura de `memory.events`) es un **ítem de iteración** menor en el primer run del gate (estilo 4.4e); el POSITIVE-OOM arranca con `--scope -p MemoryMax=64M` y se refina hasta contención verde. |
| Distinguir cgroup-OOM de `MemoryError` de Python | El hog aloca vía `bytearray` grande bajo `MemoryMax=64M` sin swap → el kernel SIGKILL (cgroup-OOM) antes de un `MemoryError` ordenado; se confirma por exit 137/kill y/o `memory.events:oom_kill` > 0 del scope. |
| `OOMPolicy=kill` + `Restart=on-failure` interfiere con el 12.7 criu (`systemctl stop`) | Un `systemctl stop` limpio NO es un fallo → no dispara `Restart=on-failure`. 12.7 está en otra branch y es independiente; al integrar, el stop limpio del orquestador criu sigue funcionando. |
| Fail-closed demasiado estricto (no arrancar sin memoria-gobierno) | Consistente con ADR-4 / 3.4 sandbox / 3.5 egress (también fail-closed). El controlador de memoria está siempre presente en el kernel target, así que en la práctica nunca bloquea un boot legítimo. |
| Techo 500 MB | Cero binarios nuevos (todo systemd/bash); sin impacto de tamaño. |

## 7. Fuera de alcance (futuro)

- **Override de `memory_max` vía machine-config** (prod tuning por nodo/perfil) — el MVP usa el default
  porcentual baked; el override sigue el patrón "valor de gate comiteado, prod reemplaza" de 3.5/4.2/4.3.
- **Load-shedding grácil app-side** — el runtime, bajo presión (`MemoryHigh`/PSI), rechazando runs nuevas
  (503) para que el trabajo en vuelo sobreviva antes del kill duro. Vertical (cambio de runtime).
- **Atribución de memoria por-agente** — heap Python compartido in-process; el por-agente causal ya se
  descartó en egress (4.4c) por pooling; aún más difícil para memoria.
- **Acción pre-OOM dirigida** por PSI (pause/evacuación, integración con 12.7) más allá del throttle que
  ya hace el kernel con `MemoryHigh`.
- **Cambios de runtime** — ninguno en 12.3-MVP.
