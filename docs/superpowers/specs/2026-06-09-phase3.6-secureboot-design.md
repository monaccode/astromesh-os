# Fase 3.6 — Secure Boot con claves propias — Diseño

> **Estado:** Diseño aprobado en brainstorm (2026-06-09).
> **Tipo:** Spec de sub-proyecto (Fase 3, Secure Boot / ADR-7). Alimenta un plan (writing-plans).
> **Precede:** Fase 3.1 (no-shell), 3.2 (AppArmor), 3.3 (TPM-sealed secret), 3.4 (sandbox) cerradas.
> Construye sobre la misma imagen, UKI y patrones de gate.

---

## 0. Contexto y propiedad objetivo

ADR-7 difirió Secure Boot a Fase 3 porque **dm-verity (Fase 2) ya cubre la integridad del root**
read-only. El valor incremental de Secure Boot es proteger la **cadena pre-verity**: firmware →
bootloader (systemd-boot) → kernel/initrd/cmdline (el UKI). Sin SB, un atacante con acceso al ESP
puede reemplazar el UKI por uno que no monta el verity (o lo monta laxo); con SB, el firmware sólo
ejecuta un UKI firmado por una clave enrolada.

**Estado actual:** mkosi 25.3 construye un **UKI Type-2** (systemd-boot, `UnifiedKernelImages=yes`).
No hay firma ni claves SB. OVMF con Secure Boot está disponible local (`OVMF_CODE_4M.secboot.fd` +
`OVMF_VARS_4M.fd` en setup-mode) y `sbsign`/`openssl`/`cert-to-efi-sig-list` presentes.

**Propiedad objetivo:** el UKI (y systemd-boot) están firmados por una clave `db` propia, enrolada en
el firmware; un boot con Secure Boot activo **sólo** ejecuta el UKI firmado, y **rechaza** un UKI
alterado/no firmado.

---

## 1. Objetivo y alcance

**Objetivo:** firmar el UKI+bootloader con un keypair propio, que systemd-boot enrole las claves en
el firmware (auto-enroll en setup-mode), y un gate que pruebe **SB activo + boot firmado healthy** y
**rechazo de un UKI corrupto**.

**Decisiones de diseño (brainstorm):**
- **Modelo de claves:** keypair propio PK/KEK/db **persistente**, generado una vez y **commiteado**
  en `phase3/secureboot/` como clave de **TEST** (claramente etiquetada dev-only; producción usaría
  un secreto de cloud). Reproducible y habilita un A/B-update-bajo-SB futuro (v2 valida con la misma
  clave). mkosi `SecureBoot=yes` firma; `SecureBootAutoEnroll=yes` hace que systemd-boot enrole las
  claves desde el ESP. Nativo de systemd-boot/UKI, **sin shim**.
- **Test negativo:** **byte-flip** del UKI firmado → firma inválida → el firmware rehúsa cargarlo.
  Simple, sin segunda clave; prueba que SB verifica firma/integridad.
- **Enroll desatendido:** `secure-boot-enroll force` en `loader.conf` para que systemd-boot enrole
  sin prompt (si no, el gate colgaría esperando input interactivo).

**En alcance (3.6):**
- Keypair de test + config `[Validation]` de mkosi (firma UKI + bootloader + auto-enroll).
- `secure-boot-enroll force` en el ESP.
- Self-check in-guest que emite `[secureboot] SB-ENABLED OK` (estado SB real vía efivars/`bootctl`).
- Gate: enroll (setup-mode → systemd-boot enrola → SB activo) → positivo (boot firmado + health +
  marcador) → negativo (UKI byte-flipped rechazado por el firmware).

**Fuera de alcance (explícito):**
- Ligar el secreto de 3.3 a **PCR 7** (estado de SB) → follow-up (requiere fusionar los gates
  SB+TPM; el gate tpm usa OVMF sin-SB hoy). No se toca 3.3.
- **A/B-update-bajo-SB** → follow-up: el gate de rollback (Fase 2) sigue usando OVMF sin-SB. (La
  clave persistente deja la puerta abierta a hacerlo después sin re-trabajo.)
- Claves de producción / provisioning por cloud (ADR-7) → fuera; sólo el modelo de test self-owned.

**Invariante:** no romper gates de Fase 0/1/2/3.1/3.2/3.3/3.4. **Firmar es backward-compatible**: los
gates sin-SB (rollback/noshell/confine/sandbox/tpm) usan OVMF **no-secboot**, que **ignora** la firma
del UKI → siguen booteando. El auto-enroll deja archivos de claves en el ESP que en firmware sin-SB
son no-ops. El plan re-corre rollback (Fase 2) + tpm (3.3) como regresión.

## 2. Claves y firma (build)

- `phase3/secureboot/db.key` + `phase3/secureboot/db.crt`: keypair RSA self-signed generado una vez
  con openssl (`openssl req -new -x509 -newkey rsa:4096 -nodes -days 3650 -subj
  "/CN=Astromesh OS SecureBoot TEST/" -keyout db.key -out db.crt`). Commiteados como **clave de
  TEST**. `phase3/secureboot/README.md` documenta que es dev-only y cómo regenerarla.
- `mkosi.conf` añade:
  ```ini
  [Validation]
  SecureBoot=yes
  SecureBootKey=phase3/secureboot/db.key
  SecureBootCertificate=phase3/secureboot/db.crt
  SecureBootAutoEnroll=yes
  ```
  Efecto: mkosi firma el UKI y el systemd-boot con la `db`, y deposita los archivos de enrolamiento
  (PK/KEK/db derivados de ese cert) en el ESP para systemd-boot.
- `loader.conf` debe tener `secure-boot-enroll force` para el enroll desatendido. Si mkosi no lo pone
  por defecto con auto-enroll, se escribe en `mkosi.postinst.chroot`/finalize (append idempotente al
  `/efi/loader/loader.conf` horneado, o vía la config de loader que mkosi genera).

## 3. Self-check in-guest (`phase3/secureboot/secureboot-check.{sh,service}`)

Oneshot (patrón de 3.2/3.4), corre en boot, emite marcadores a consola:
- Lee el estado de Secure Boot desde la efivar `SecureBoot-8be4df61-93ca-11d2-aa0d-00e098032b8c`
  (último byte = 1 ⇒ activo) o `bootctl status` (línea "Secure Boot: enabled").
- `[secureboot] SB-ENABLED OK` si SB activo; `[secureboot] SB FAILED` + exit≠0 si no.
- (Nota: en un boot sin-SB —los otros gates— el self-check reporta SB-disabled y NO falla el boot;
  sólo el gate de 3.6 exige SB-ENABLED. El self-check distingue "SB off" (degradado, log) de un fallo
  real. Es decir: marca `SB-ENABLED OK` sólo bajo SB; bajo no-SB emite un log informativo y exit 0,
  para no romper los gates Fase 0/2/3.1/3.2/3.3/3.4 que arrancan sin SB.)

## 4. El gate (`tests/boot/secureboot-and-assert.sh`)

Reusa `lib-esp.sh` (montar el ESP para el byte-flip). OVMF: prefiere `OVMF_CODE_4M.secboot.fd`.
1. **Enroll:** QEMU persistente con `OVMF_CODE_4M.secboot.fd` + copia fresca de `OVMF_VARS_4M.fd`
   (setup-mode). systemd-boot ve las claves de auto-enroll, las enrola (`secure-boot-enroll force`),
   sale de setup-mode → SB activo → reboot (mismo QEMU persistente, o se reinicia con las VARS ya
   enroladas que se persisten).
2. **Positivo:** bajo SB activo, el UKI firmado bootea → `/v1/health` 200 y el marcador
   `[secureboot] SB-ENABLED OK` aparece en consola. (Confirma firma válida + SB enforcing + runtime
   sano bajo SB.)
3. **Negativo:** copiar el disco, montar el ESP, **alterar un byte** del UKI firmado
   (`/EFI/Linux/*.efi`), arrancar con las VARS enroladas → el firmware **rechaza** (security
   violation / no carga el kernel) → el harness verifica que `/v1/health` **no** sube y/o que la
   consola muestra el rechazo. Marcador final: `[secureboot] SECUREBOOT GATE PASSED`.

## 6. Criterios de done

- Local `dev-loop.sh secureboot` → `SECUREBOOT GATE PASSED`: SB activo + UKI firmado healthy +
  `SB-ENABLED OK`; UKI corrupto **rechazado** por el firmware.
- CI `phase3-secureboot.yml` verde incluyendo `secureboot-gate`.
- Gates de Fase 0/2/3.1/3.2/3.3/3.4 siguen verdes (firmar es backward-compatible; el self-check no
  falla en boots sin-SB). Regresión: rollback (Fase 2) + tpm (3.3).
- Spec roadmap de Fase 3 actualizado; 3.6 marcado done con referencia de run.

## 7. Riesgos

| Riesgo | Mitigación |
|---|---|
| Enroll desatendido cuelga esperando input | `secure-boot-enroll force` en `loader.conf` (verificar que mkosi lo ponga o escribirlo en postinst). |
| OVMF secboot no presente en el runner CI | El paquete `ovmf` de ubuntu provee `OVMF_CODE_4M.secboot.fd`; el gate prefiere el CODE `.secboot` con fallback claro y FAIL explícito si no hay variante SB. |
| Lentitud TCG en el doble-boot de enroll | Timeouts generosos (≥240s por boot) como en los otros gates; el enroll-reboot es una sola vez. |
| Firmar rompe los gates sin-SB | OVMF no-secboot ignora la firma → boota igual; auto-enroll keys en ESP son no-op sin SB. Validado por la regresión rollback/tpm. |
| Clave privada de test commiteada (secret-scanners / mal uso) | Etiquetar INSECURE/dev-only en README y en el subject del cert (`CN=...TEST`); documentar que producción usa secreto de cloud. No es una clave real. |
| systemd-boot no firmado / mkosi no firma el bootloader | `SecureBoot=yes` firma tanto el UKI como el systemd-boot que mkosi instala; verificar con `sbverify` en el gate si el firmware rechaza el bootloader. |
| El byte-flip cae en una zona que no invalida la firma Authenticode | Alterar un byte del **payload** del PE (p.ej. dentro de `.linux`/cabecera), no en zonas excluidas del hash Authenticode; verificar que el firmware efectivamente rechaza (el gate falla si bootea). |
