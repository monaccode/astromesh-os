# Fase 3.3 — TPM-sealed secret (provider key, PCR-bound) — Diseño

> **Estado:** Diseño aprobado en brainstorm (2026-06-09).
> **Tipo:** Spec de sub-proyecto (Fase 3, sub-proyecto D parcial). Alimenta un plan (writing-plans).
> **Precede:** Fase 3.1 (no-shell+break-glass) y 3.2 (AppArmor) cerradas. Construye sobre la misma imagen.

---

## 0. Contexto y propiedad objetivo

Gate de Fase 3 (decomposición §6.5): **"secreto accesible SOLO con boot íntegro"**. Hoy
`OPENAI_API_KEY` se hornea en `/etc/astromesh/.env` (root verity read-only) — legible bajo
**cualquier** boot, así que sellarlo no bastaría: el plaintext está en la imagen. 3.3 cambia el
modelo de aprovisionamiento: el secreto **no se hornea**, se **aprovisiona en el primer boot**,
se **sella al TPM ligado a PCR 11**, y de ahí en más sólo se recupera por **TPM-unseal**, que
tiene éxito únicamente bajo el UKI/cmdline íntegro → root verity íntegro.

**Por qué PCR 11:** systemd-stub mide el UKI (kernel/initrd/**cmdline**, y el cmdline lleva
`roothash=`) en PCR 11. Sellar a PCR 11 ata el secreto al boot exacto: un UKI o cmdline alterado
→ PCR 11 distinto → unseal falla.

Estado actual confirmado: `swtpm` instalable (WSL/CI), QEMU soporta `-tpmdev emulator`,
`systemd-creds` está en el systemd 257 de la imagen. astromeshd lee `OPENAI_API_KEY` vía
`EnvironmentFile=-/etc/astromesh/.env` (`api_key_env: OPENAI_API_KEY` en el agent YAML).

---

## 1. Objetivo y alcance

**Objetivo:** que `OPENAI_API_KEY` esté disponible para astromeshd **sólo bajo boot íntegro**,
sellándolo al TPM ligado a PCR 11; un boot alterado (cmdline distinto → PCR 11 distinto) no
puede des-sellarlo.

**En alcance (3.3):**
- Quitar el plaintext horneado del `.env`.
- Aprovisionar la key en el primer boot vía credencial SMBIOS de systemd.
- Sellar a TPM+PCR11 (`systemd-creds`), des-sellar en cada boot a un `.env` en tmpfs que
  astromeshd carga.
- Gate: intacto → unseal OK + astromeshd funcional; alterado → unseal falla.

**Fuera de alcance (explícito):**
- Secure Boot / PCR 7 (→ 3.6).
- Atestación remota (sub-proyecto posterior).
- Sellar la credencial break-glass de 3.1 (follow-up).
- Confianza cero en el canal de aprovisionamiento: el SMBIOS del primer boot se asume confiable
  (es el momento de provisioning); 3.3 protege la disponibilidad **runtime** del secreto.

**Invariante:** no romper gates de Fase 0/1/2/3.1/3.2 (health, A/B update, rollback, no-shell,
confinamiento). El cambio de `EnvironmentFile` no debe romper el arranque de astromeshd; el plan
re-corre rollback (Fase 2) y confine (3.2) como regresión.

## 2. Aprovisionamiento + sellado (primer boot)

- `mkosi.postinst.chroot`: el `.env` horneado **deja de contener** `OPENAI_API_KEY` (sólo queda,
  si acaso, lo que no es secreto). El plaintext no se hornea.
- Aprovisionamiento: credencial SMBIOS tipo 11 `io.systemd.credential:astromesh.openai_key=<key>`,
  pasada por el harness (y por la plataforma en cloud). systemd la expone vía `ImportCredential=`.
- `phase3/tpm/astromesh-seal-secret.{sh,service}` (oneshot, corre **sólo si no existe** el blob
  sellado — guard de primer boot):
  - lee la credencial aprovisionada (`$CREDENTIALS_DIRECTORY/astromesh.openai_key`),
  - sella: `systemd-creds encrypt --name=astromesh.openai_key --with-key=tpm2 --tpm2-pcrs=11
    <plaintext> /var/lib/astromesh/secrets/openai.cred`,
  - el plaintext nunca se persiste (la credencial SMBIOS es transitoria en `/run`).
  - Si no hay credencial Y no hay blob (p.ej. boot sin provisioning) → log claro y no falla el
    boot (astromeshd quedará sin key, modo degradado — fail-closed para el secreto, no para el boot).

## 3. Des-sellado (cada boot, antes de astromeshd)

- `phase3/tpm/astromesh-unseal-secret.{sh,service}` (oneshot, `Before=astromeshd.service`):
  - `systemd-creds decrypt /var/lib/astromesh/secrets/openai.cred -` → si PCR 11 coincide
    (boot íntegro), entrega el plaintext;
  - escribe `OPENAI_API_KEY=<key>` a `/run/astromesh/env` (tmpfs, 0640 root:astromesh);
  - si el unseal **falla** (PCR distinto / boot alterado) → NO escribe `/run/astromesh/env`
    (astromeshd arranca sin la key).
- Drop-in `phase3/tpm/10-sealed-env.conf` en `astromeshd.service.d/`:
  `EnvironmentFile=-/run/astromesh/env` (el `-` lo hace opcional: ausencia = sin key, no falla
  el arranque del unit).

## 4. Harness (swtpm + TPM + SMBIOS)

- Instalar `swtpm` en el runner; estado persistente en un dir (SRK estable entre reboots del gate).
- QEMU: `-tpmdev emulator,id=tpm0,chardev=chrtpm -chardev socket,id=chrtpm,path=<swtpm-sock>
  -device tpm-tis,tpmdev=tpm0`.
- Primer boot: `-smbios type=11,value=io.systemd.credential:astromesh.openai_key=<dummy-key>`.
- qcow2 persistente a través de los reboots del gate (el blob sellado vive en `/var`).

## 5. El gate (`tests/boot/tpm-seal-and-assert.sh`)

QEMU persistente con swtpm (KVM local / TCG CI). Un self-check in-guest
(`phase3/tpm/seal-check.{sh,service}`) emite marcadores a consola; el harness verifica
health+query y grepea los marcadores.

1. **Boot 1 (intacto, +TPM +SMBIOS):** seal-secret sella; unseal-secret des-sella a `/run`;
   astromeshd `/v1/health` 200 + query OK (tiene la key). Marcadores: `[seal] SEALED OK`,
   `[seal] UNSEAL OK`.
2. **Boot 2 (mismo disco, cmdline alterado):** el harness usa el driver pexpect del menú
   systemd-boot (patrón de 3.1) para append un token al cmdline → PCR 11 distinto → unseal
   **falla** → `/run/astromesh/env` ausente. Marcador: `[seal] TAMPER-BLOCKED OK` (el secreto
   no se des-selló bajo boot alterado). Verdict final del harness: `TPM SEAL GATE PASSED`.

> El marcador de boot 2 lo emite el unseal-service/self-check al detectar que el decrypt falló y
> no hay `/run/astromesh/env`; el harness lo grepea. (El positivo del boot 1 y el negativo del
> boot 2 juntos prueban "secreto sólo bajo boot íntegro".)

## 7. Criterios de done

- Local `dev-loop.sh tpm` → `TPM SEAL GATE PASSED` (intacto: seal+unseal+astromeshd funcional;
  alterado: unseal falla).
- CI `phase3-tpm.yml` verde incluyendo `tpm-seal-gate`.
- Gates de Fase 0/2/3.1/3.2 siguen verdes (el cambio de secreto no rompió health/update/rollback/
  no-shell/confine).
- La imagen **no** hornea `OPENAI_API_KEY` en plaintext.
- Spec roadmap de Fase 3 actualizado; 3.3 marcado done con referencia de run.

## 8. Riesgos

| Riesgo | Mitigación |
|---|---|
| systemd-creds + PCR 11 bajo swtpm finicky | Empezar con seal/unseal en el mismo boot; loguear PCR 11 (`systemd-analyze pcrs`) para diagnosticar; iterar como 3.1/3.2 |
| swtpm: SRK/estado no persiste entre reboots del gate | swtpm con `--tpmstate` dir persistente; un solo proceso swtpm vivo durante todos los boots del gate |
| systemd-stub no mide PCR 11 sin TPM presente | El harness siempre arranca con swtpm; verificar que PCR 11 ≠ 0 en boot 1 |
| El cmdline alterado no mueve PCR 11 | systemd-stub mide el cmdline en PCR 11; verificar que el token aparece en `/proc/cmdline` y el unseal falla |
| Cambio de `EnvironmentFile` rompe astromeshd | `EnvironmentFile=-` (opcional); mantener el `/etc/.env` para lo no-secreto; regresión de health |
| Aprovisionamiento SMBIOS no llega | Verificar `ImportCredential` / `$CREDENTIALS_DIRECTORY`; fallback de log claro |
| Plaintext del secreto se filtra a `/var` o logs | Sellar desde la credencial transitoria; nunca escribir el plaintext salvo a `/run` (tmpfs) en unseal |
