# Fase 4.4b — Export OTel del mapa de egress por-flujo (eBPF → OTLP) — Diseño

> **Estado:** Diseño aprobado en brainstorm (2026-06-10).
> **Tipo:** Refinamiento de Fase 4 (cierra el círculo §6.8↔§12.6: la atribución eBPF de 4.4 sale por el
> pipeline OTLP de 4.3).
> **Precede:** 4.4 (mapa eBPF `flows`) + 4.3 (collector OTLP).
> **Alcance elegido (brainstorm):** **export OTel** del mapa por-flujo (por-dst). El join **por-agente**
> (socket-cookie→agent-run) queda como **4.4c** — requiere cambio de runtime + helper privilegiado.

---

## 0. Contexto y propiedad objetivo

4.4 entregó la contabilidad eBPF de egress por-flujo (mapa `flows` en `/sys/fs/bpf/astromesh/flows`,
`{daddr,dport,proto}→{bytes,packets}`). 4.3 entregó el collector OTLP. 4.4b las une: las métricas de
atribución salen del nodo vía OTLP al collector — cerrando el círculo de observabilidad (§6.8) con la
señal causal de kernel (§12.6).

### 0.1 Restricción load-bearing (discovery)

- **astromeshd es non-root** (`User=astromesh`, `NoNewPrivileges=yes`, sin capabilities) y Debian trae
  `unprivileged_bpf_disabled` → **astromeshd NO puede leer el mapa BPF** (ni `bpf()` ni `bpftool`). Por
  eso el exporter debe ser un **componente privilegiado (root)**, no parte del runtime.
- **El venv ya tiene el SDK de métricas:** `opentelemetry.sdk.metrics` (MeterProvider) +
  `opentelemetry.exporter.otlp.proto.grpc.metric_exporter` (OTLPMetricExporter) están en el venv del
  `.deb` (extra `observability` de 4.3). → el exporter root reusa `/opt/astromesh/venv/bin/python3`,
  **sin cambio de runtime**.
- **El collector ocb de 4.3 ya soporta métricas:** otlpreceiver + batchprocessor + debugexporter manejan
  traces **y** metrics; solo falta agregar un pipeline `metrics` al `otelcol.yaml` (no se rebuildea el
  binario).
- **Sin feedback:** el exporter corre en su propia unit (no en el cgroup de astromeshd), así que su
  tráfico OTLP a `127.0.0.1:4317` **no** lo cuenta el eBPF (que está atado al cgroup de astromeshd).

## 1. Arquitectura y flujo de datos

```
mapa eBPF "flows" (4.4)  /sys/fs/bpf/astromesh/flows   {daddr,dport,proto}->{bytes,packets}
   │ (root)
   ▼
egress-otlp-export.py (oneshot ROOT, timer cada 10s)
   │ bpftool -j map dump  →  parse (misma lógica que egress-acct-dump.sh)
   │ venv python + OTel SDK: Gauge astromesh.egress.bytes{daddr,dport,proto} + .packets (valor del mapa)
   ▼ OTLP/gRPC → 127.0.0.1:4317  (force_flush, como 4.3)
otelcol sidecar (4.3)  [pipeline `metrics` nuevo: otlp → batch → debug]  → debug → consola
   ▼
gate: asserta la métrica del flujo del stub (dport=8081) en el dump del collector
```

Un solo VM. El exporter es oneshot+timer (mismo patrón que el dump-timer de 4.4): cada 10s lee el mapa,
construye las métricas y hace force_flush al collector.

## 3. El gate (`tests/boot/ebpf-otlp-and-assert.sh`)

1. Boot 1 VM con machine-config `ebpf_egress: true` + `otel: true`.
2. Assert consola: `[ebpf] EBPF-EGRESS-ATTACHED OK` + `[otel] OTEL-COLLECTOR OK`.
3. Espera `/v1/health`; POST corridas al `phase0-smoke` (stub) → flujo a `127.0.0.1:8081` contado por el eBPF.
4. El timer del exporter (cada 10s) emite la métrica; el collector la vuelca por `debug`.
5. Assert consola: el collector dumpeó una métrica `astromesh.egress.bytes` con `dport=8081` y valor>0
   (`Metric #… Name: astromesh.egress.bytes … dport: 8081`). Marker `[ebpf] EBPF-OTLP-EXPORTED OK`.
6. `[ebpf] EBPF OTLP GATE PASSED`.

**Discovery+iterate:** el formato del debug-exporter para métricas (`Metric #`/`DataPoints`/atributos) se
confirma en el primer run y se ajusta el grep (como el de trazas de 4.3). Si el gauge no aparece, dump
del bloque `Metric`/`ResourceMetrics` del collector.

## 4. Criterios de done

- Local `dev-loop.sh ebpf-otlp` → `EBPF OTLP GATE PASSED` (métrica de egress del stub en el collector).
- CI `phase4-ebpf-otlp.yml` verde.
- Gates previos verdes: `otel` (el pipeline de traces sigue), `ebpf` (la contabilidad sigue), egress/
  machineconfig. La guarda (ebpf **y** otel) no-opea el exporter fuera del boot combinado.
- Roadmap: 4.4b marcado done.

---

## 5. Riesgos

| Riesgo | Mitigación |
|---|---|
| astromeshd non-root no puede leer el mapa | El exporter es una unit **root** separada que reusa el venv; no toca al runtime. |
| El collector de 4.3 no acepta métricas | El ocb ya trae otlp/batch/debug para métricas; solo se agrega el pipeline `metrics` al YAML (sin rebuild). |
| Feedback (el OTLP del exporter contado por el eBPF) | El exporter no está en el cgroup de astromeshd → su tráfico no se cuenta. |
| Formato del debug-exporter para métricas | Discovery+iterate en el gate (como las trazas de 4.3). |
| Cambiar comportamiento de gates previos | Guarda por `ebpf.egress.enabled` **y** `observability.otlp.enabled`; fuera del boot combinado es no-op. |

## 6. Fuera de alcance (futuro)

- **4.4c join por-agente:** el runtime registra `socket-cookie→agent-run` (vía endpoint/archivo), un
  helper root lo sincroniza a un mapa BPF, y el eBPF re-keya los flujos por agente; el exporter emite
  bytes **por-agente**. (SO_MARK está bloqueado: astromeshd non-root sin CAP_NET_ADMIN.)
- **Control Rust** (libbpf-rs) que reemplaza bpftool/python — la base R3 de §12.
- IPv6/ingress y otras dimensiones.
