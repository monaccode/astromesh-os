# Fase 4.4d — Control Rust del eBPF (libbpf-rs + OTLP) — Diseño

> **Estado:** Diseño aprobado en brainstorm (2026-06-10).
> **Tipo:** Refactor de Fase 4 — reemplaza el userspace de eBPF de 4.4/4.4b (bash + python + bpftool)
> por **un daemon Rust** (libbpf-rs + opentelemetry-rust). Es la base R3 de §12 ("control: Rust").
> **Precede/reemplaza:** 4.4 (egress-acct) + 4.4b (egress-otlp-export). El eBPF en C se queda.
> **Alcance elegido (brainstorm):** **control completo** — load + attach + read + OTLP export en una sola
> pieza Rust. Mismo comportamiento externo (métrica de egress por-flujo al collector), userspace nuevo.

---

## 0. Contexto y propiedad objetivo

ADR-10/§13.3: el perfil **systems/kernel engineer (Rust+eBPF)** es la dependencia de talento crítica
(R3); sin Rust+eBPF, §12 "colapsa a una distro con tunables". 4.4 y 4.4b probaron la atribución eBPF
con userspace de bash+python+bpftool (pragmático para el MVP). 4.4d entrega la **base de control en
Rust**: un daemon `astromesh-ebpf` que, vía **libbpf-rs**, carga el programa eBPF (skeleton embebido),
lo atacha, lee el mapa y exporta las métricas OTLP — reemplazando los scripts y `bpftool`. Es el
fundamento sobre el que se construye el control real de §12 (decisiones, no solo telemetría).

### 0.1 Realidad (discovery)

- **Toolchain (apt):** `rustc`/`cargo` (1.85), `clang` (19), `libbpf-dev` (1.5) — instalables en host/CI.
- **libbpf-rs:** `build.rs` usa `libbpf_cargo::SkeletonBuilder` para compilar `egress_acct.bpf.c` (clang)
  en un **skeleton embebido** en el binario → **sin `.bpf.o` separado** en runtime. El programa es
  "clásico" (uapi headers, sin vmlinux.h) — el build necesita el include de arch (`-I.../x86_64-linux-gnu`),
  como ya vimos en 4.4. **Build = riesgo alto → discovery+iterate (probar mínimo en host primero).**
- **Linkeo:** libbpf-sys puede **vendorizar + linkear estático** libbpf; libelf/zlib son deps de libbpf
  (estático con `static` feature, o dinámico + hornear `libelf1`/`zlib1g`). Decidir en discovery.
- **OTLP en Rust:** `opentelemetry` + `opentelemetry_sdk` + `opentelemetry-otlp` (tonic/gRPC) exportan a
  `http://127.0.0.1:4317` **insecure** (h2 plano, sin TLS para loopback). El collector de 4.3+4.4b ya
  recibe métricas.
- **Entrega:** `cargo build --release` en host/CI → `dist/astromesh-ebpf` (build-input, como otelcol; el
  postinst no tiene cargo/red). Horneado solo si está presente.
- **Coexistencia con 3.5:** `BPF_F_ALLOW_MULTI` al atachar (ya validado en 4.4).

## 1. Arquitectura y flujo de datos

```
astromesh-ebpf (daemon Rust, ROOT)   build-input dist/astromesh-ebpf
  ├─ libbpf-rs: open+load del skeleton embebido (egress_acct.bpf.c)
  ├─ attach cgroup_skb/egress al cgroup de astromeshd (multi)
  ├─ loop cada 10s: itera el mapa flows {daddr,dport,proto}->{bytes,packets}
  └─ opentelemetry-otlp/tonic: ObservableGauge astromesh.egress.{bytes,packets}{daddr,dport,proto}
       ▼ OTLP/gRPC → 127.0.0.1:4317
otelcol sidecar (4.3 + pipeline metrics de 4.4b) → debug → consola
       ▼
gate: asserta astromesh.egress.bytes{dport=8081} en el dump del collector
```

Un solo VM. El daemon corre como **root** (astromeshd es non-root y no puede tocar BPF, igual que 4.4b).
Reemplaza todo el userspace de bash/python/bpftool por una pieza Rust.

## 3. El gate (`tests/boot/ebpf-rust-and-assert.sh`)

1. Boot 1 VM con machine-config `ebpf_egress: true` + `otel: true`.
2. Assert consola: `[otel] OTEL-COLLECTOR OK` + el daemon logueó `ASTROMESH-EBPF ATTACHED OK`.
3. Espera `/v1/health`; POST corridas al `phase0-smoke` (stub) → flujo a `127.0.0.1:8081`.
4. Assert consola: el collector dumpeó `astromesh.egress.bytes` con `dport: Int(8081)` y `Value>0` (mismo
   contrato que 4.4b, ahora vía el daemon Rust). Marker `[otel] EBPF-RUST-EXPORTED OK`.
5. `[otel] EBPF-RUST GATE PASSED`.

**Discovery+iterate:** (a) el build de libbpf-rs (skeleton + linkeo) se prueba en host antes de cablear;
(b) el formato de la métrica del debug-exporter ya se conoce de 4.4b (`Name: astromesh.egress.bytes`,
`dport: Int(8081)`).

## 4. Criterios de done

- Local `dev-loop.sh ebpf-rust` → `EBPF-RUST GATE PASSED` (el daemon Rust atacha + exporta la métrica).
- CI `phase4-ebpf-rust.yml` verde.
- Gates previos verdes: `otel` (trazas), `egress`/`machineconfig`/`mesh`. La guarda doble no-opea el
  daemon fuera del boot combinado.
- El userspace viejo (bash/python/bpftool) **removido**; `bpftool` ya no está en la imagen.
- Roadmap: 4.4d marcado done.

## 5. Riesgos

| Riesgo | Mitigación |
|---|---|
| **Build de libbpf-rs** (libbpf-cargo + skeleton + linkeo) — el riesgo más alto | Discovery+iterate: probar un build mínimo en host (skeleton + load) ANTES de cablear todo. Toolchain disponible. |
| Linkeo estático de libbpf/libelf/zlib | `static` feature de libbpf-sys, o dinámico + hornear `libelf1`/`zlib1g` (chico). Decidir en el build. |
| OTLP en Rust (tonic) | `opentelemetry-otlp` insecure a loopback (h2 plano); sin TLS. Probar el export en host (como 4.4b). |
| Remover el userspace viejo rompe gates | 4.4d reemplaza por un gate consolidado; comportamiento externo idéntico (métrica al collector). |
| Tamaño del binario Rust en la raíz de 448M | Un binario libbpf-rs+tonic es chico (~pocos MB); horneado solo en builds ebpf. |
| Coexistencia con el filtro de 3.5 | `BPF_F_ALLOW_MULTI` (ya validado en 4.4). |
