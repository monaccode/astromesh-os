# Fase 4.1 — machine-config declarativo (perfil + identidad del nodo, sin SSH) — Diseño

> **Estado:** Diseño aprobado en brainstorm (2026-06-09).
> **Tipo:** Spec de sub-proyecto (Fase 4, sub-proyecto **C** parcial — primera rebanada).
> **Precede:** Fase 3 completa (3.1 no-shell, 3.2 AppArmor, 3.3 TPM-seal, 3.4 sandbox, 3.5 egress,
> 3.6 Secure Boot). Construye sobre la misma imagen y patrones de gate.

---

## 0. Contexto y propiedad objetivo

Gate de Fase 4 (decomposición, tabla de fases — fila Fase 4): **"el nodo joinea la malla solo con
machine-config (sin SSH)"**.
Esta sub-fase entrega la **raíz** de ese gate: la superficie declarativa que configura el nodo al
boot. La malla en sí (join entre nodos, auth mTLS+TPM) es 4.2; el provisioning multi-cloud es 4.5.

**Realidad actual (clave para el alcance):** hoy la imagen **hornea estáticamente** la config del
nodo — el postinst instala UN agent YAML en `/etc/astromesh/agents/` y el rol no se elige (no hay
`runtime.yaml`; el nodo corre el agente horneado). El runtime tiene **7 perfiles** bundled
(`config/profiles/{full,gateway,inference,worker,mesh-gateway,mesh-inference,mesh-worker}.yaml`) y
sabe renderizar `runtime.yaml` desde un perfil (`astromesh-node` CLI: `runtime.yaml` ← `profiles/<role>.yaml`),
pero el OS no expone esa elección de forma declarativa.

**Decisión de alcance (brainstorm):** 4.1 introduce un **machine-config** inyectado por **credencial
SMBIOS tipo 11** (mismo canal que la provider key de 3.3) que, al boot y **antes de astromeshd**,
selecciona el **perfil** (rol del nodo) y fija la **identidad** (`node_id`/hostname). El mismo disco
bootea como gateway/worker/inference/etc. según la config inyectada — sin SSH, sin hornear el rol.

**Por qué SMBIOS y no config-drive/URL:** 3.3 ya estableció el canal de credenciales SMBIOS
(`io.systemd.credential:...` → `$CREDENTIALS_DIRECTORY`), cloud-native y sin red al boot. Reusarlo es
mínima maquinaria nueva y testeable idéntico a 3.3 (`-smbios type=11`). Una partición config-drive
(más capacidad, útil cuando 4.2 sume certs/peers de malla) queda como evolución documentada; un fetch
por URL choca con el egress deny-by-default de 3.5 (requeriría red al boot). Capacidad SMBIOS (KB)
sobra para perfil+identidad.

**Fuera de alcance (explícito):**
- Membership de malla / peers / join (→ 4.2).
- Auth mTLS + atestación TPM antes del join (→ 4.2, cierra R2).
- Provisioning multi-cloud AKS/EKS/GKE (→ 4.5, no testeable local).
- Config de provider (endpoint/modelo) por machine-config: la KEY la maneja 3.3 (TPM); el endpoint
  hoy vive en el agent YAML — no se mueve en 4.1 (YAGNI; se reevaluará en 4.2/4.3).
- sysext-gpu (opcional, diferido).

**Invariante:** no romper gates de Fase 0/1/2/3 (health, A/B update, rollback, no-shell, confine,
TPM-unseal, sandbox, egress, Secure Boot). Esos gates bootean **sin** machine-config, así que la
ausencia de machine-config debe ser **no-fatal** y mantener el comportamiento horneado actual. El
plan re-corre rollback (Fase 2) y un gate de Fase 3 como regresión.

## 1. Objetivo y alcance

**Objetivo:** que el rol (perfil) y la identidad (`node_id`/hostname) del nodo provengan de un
machine-config declarativo inyectado por SMBIOS al boot — no horneado, no por SSH — y que el mismo
disco se configure como cualquiera de los 7 roles según esa config.

**En alcance (4.1):**
- Formato del machine-config (YAML chico: `profile` + `node_id` + `hostname?`).
- Oneshot `Before=astromeshd` que lee la credencial, valida el perfil, renderiza `runtime.yaml`
  desde el perfil elegido a ruta escribible, fija identidad, y emite marcadores.
- Fallback no-fatal: sin machine-config → log claro + mantener default horneado.
- Drop-in que apunta astromeshd al `runtime.yaml` renderizado (`ASTROMESH_CONFIG_DIR`).
- Gate de boot (KVM local + CI): 2 boots del mismo disco con machine-configs distintos → roles
  distintos aplicados + astromeshd healthy.

---

## 2. Formato del machine-config

Credencial SMBIOS tipo 11: `io.systemd.credential:astromesh.machine_config=<contenido>`. systemd la
expone en `$CREDENTIALS_DIRECTORY/astromesh.machine_config` (vía `ImportCredential=astromesh.machine_config`
o `LoadCredential=`). Contenido YAML mínimo:

```yaml
profile: worker          # uno de los 7 roles bundled del runtime (validado; desconocido → FAIL)
node_id: node-a          # identidad estable del nodo (la malla 4.2 la usará)
hostname: node-a         # opcional; si ausente, se deriva de node_id
```

- **Parseo robusto:** el oneshot usa un parser YAML disponible en la imagen (`python3` del venv, que
  trae PyYAML) — no un grep frágil. Campos desconocidos se ignoran (forward-compat para 4.2).
- **Validación fail-closed:** `profile` debe existir como `<profiles_dir>/<profile>.yaml`; si no →
  marcador `[mcfg] FAIL: unknown profile` + exit≠0 (el nodo no asume un rol inválido).

## 3. Aplicación (oneshot, antes de astromeshd)

`phase4/machineconfig/astromesh-machine-config.{sh,service}` — oneshot `Before=astromeshd.service`,
con `ImportCredential=astromesh.machine_config`. El script (`set -uo pipefail`):

1. **Sin credencial** → `[mcfg] no machine-config; keeping baked default` + exit 0 (fallback
   no-fatal — no rompe Fase 0/2/3).
2. Parsea `profile`/`node_id`/`hostname` (python3 + PyYAML).
3. Valida `profile` contra los perfiles bundled (descubiertos en la imagen, p.ej.
   `/opt/astromesh/venv/lib/python*/site-packages/astromesh/_bundled/config/profiles/` o la ruta que
   el plan confirme). Desconocido → `[mcfg] FAIL: unknown profile=<p>` + exit 1.
4. **Renderiza `runtime.yaml`** desde el perfil elegido a una **ruta escribible** y apunta astromeshd
   ahí. El plan resuelve la ruta exacta: `/etc/astromesh/runtime.yaml` si `/etc` es overlay-escribible,
   o `/run/astromesh/config/` con `ASTROMESH_CONFIG_DIR` por drop-in (preferido: evita depender de
   /etc; se enlazan los `agents/` existentes ahí). La forma de render: copiar el perfil bundled a
   `runtime.yaml` (mínimo), o invocar el render del runtime si es barato — el plan elige tras un
   discovery del CLI `astromesh-node`.
5. **Identidad:** `hostnamectl set-hostname <hostname|node_id>` (hostname transient en `/run` — anda
   con `/etc` read-only) + persiste `node_id` en `/var/lib/astromesh/node-id` (0644; la malla 4.2 lo
   lee como identidad estable).
6. Markers a consola (`StandardOutput=journal+console`): `[mcfg] APPLIED profile=<role> node=<id> OK`.

**Drop-in** `phase4/machineconfig/15-machine-config.conf` en `astromeshd.service.d/`:
`Environment=ASTROMESH_CONFIG_DIR=<ruta-render>` (si se usa /run) + `Requires=`/`After=` el oneshot
**sólo si** queremos que un FAIL de validación (perfil inválido) impida el arranque. **Decisión:** el
oneshot es `Wants=`/`Before=` (no `Requires=`) — un perfil inválido falla el oneshot y deja al nodo
en default horneado con un marcador de error visible, pero **no** tumba astromeshd (evita acoplar el
arranque del runtime a un typo de machine-config). El fail-closed de validación se refleja en el
**gate** (un perfil inválido es rojo), no en el boot productivo.

## 4. El gate (`tests/boot/machineconfig-and-assert.sh`)

QEMU (KVM local / TCG CI), patrón de los gates de Fase 3, **2 boots del mismo disco** con
machine-configs distintos vía SMBIOS:

1. **Boot A** — `-smbios type=11,value=io.systemd.credential:astromesh.machine_config=<yaml worker>`
   (`profile: worker, node_id: node-a`):
   - `/v1/health` 200 (el render no rompió astromeshd),
   - marker `[mcfg] APPLIED profile=worker node=node-a OK`,
   - assert in-guest/console: el `runtime.yaml` activo proviene del perfil **worker** (el self-check
     o el harness verifica un campo distintivo del perfil worker), hostname=`node-a`.
2. **Boot B** — mismo disco, `profile: gateway, node_id: node-b`:
   - marker `[mcfg] APPLIED profile=gateway node=node-b OK`, `runtime.yaml` = **gateway**,
     hostname=`node-b`.
   - Prueba la **configurabilidad declarativa**: el mismo disco asume un rol distinto sólo por el
     machine-config (sin SSH, sin rebuild).
3. (No-SSH ya lo garantiza el gate de 3.1; este gate lo **referencia**, no lo re-prueba.)
4. Veredicto: `[mcfg] MACHINECONFIG GATE PASSED`.

> Cómo el gate "ve" el rol aplicado: el oneshot emite el marker con el perfil, y además el harness
> lee un campo distintivo del `runtime.yaml` renderizado (p.ej. vía un endpoint del runtime que
> reporte el perfil/config activo, o leyendo el archivo por consola con un self-check). El plan elige
> el método tras confirmar qué expone el runtime (`/v1/...` o un marcador propio).

## 6. Criterios de done

- Local `dev-loop.sh machineconfig` → `MACHINECONFIG GATE PASSED` (boot A worker + boot B gateway,
  cada uno con su rol+identidad aplicados y astromeshd healthy).
- CI `phase4-machineconfig.yml` verde incluyendo `machineconfig-gate`.
- Gates de Fase 0/2/3 siguen verdes (sin machine-config → default horneado; el oneshot es no-fatal).
- La imagen **no** hornea el rol: el rol proviene del machine-config (o cae al default sólo en su
  ausencia).
- Spec roadmap de Fase 4 creado; 4.1 marcado done con referencia de run.

## 7. Riesgos

| Riesgo | Mitigación |
|---|---|
| El runtime no toma `runtime.yaml` desde la ruta renderizada | `ASTROMESH_CONFIG_DIR` por drop-in apunta a la ruta escribible; el plan hace un discovery de `_resolve_config_dir()` y valida con health bajo el perfil renderizado. |
| `/etc/astromesh` no es escribible en runtime (verity) | Render a `/run/astromesh/config/` (tmpfs, escribible) + `ASTROMESH_CONFIG_DIR`; se enlazan los `agents/` baked ahí. Evita depender de overlay de /etc. |
| Perfiles bundled en ruta distinta a la asumida | El oneshot **descubre** la ruta de `profiles/` en la imagen (no hardcode); el plan confirma con un `find` en un build. |
| `hostnamectl set-hostname` falla bajo el sandbox/seccomp de 3.4 | El oneshot corre como unit propia (no bajo el drop-in de astromeshd); `hostnamed` usa D-Bus. Validar en el gate; fallback: escribir `/run/hostname` + `sethostname()`. |
| La credencial SMBIOS no llega / `ImportCredential` no la expone | Verificar `$CREDENTIALS_DIRECTORY/astromesh.machine_config`; mismo mecanismo ya probado en 3.3 (reusar su patrón exacto). |
| Acoplar astromeshd a un typo de machine-config (perfil inválido tumba el runtime) | El oneshot es `Wants=`/`Before=` (no `Requires=`): perfil inválido → marker de error + default horneado, no rompe el boot productivo; el gate sí lo marca rojo. |
| Romper Fase 0/2/3 (que bootean sin machine-config) | Fallback no-fatal (ausencia → default horneado + exit 0); regresión de rollback + un gate de Fase 3. |
