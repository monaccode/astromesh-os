# Fase 3.4 — E-MVP sandbox del runtime (seccomp + namespaces + privilegios) — Diseño

> **Estado:** Diseño aprobado en brainstorm (2026-06-09).
> **Tipo:** Spec de sub-proyecto (Fase 3, sub-proyecto **E**-MVP). Alimenta un plan (writing-plans).
> **Precede:** Fase 3.1 (no-shell+break-glass), 3.2 (AppArmor), 3.3 (TPM-sealed secret) cerradas.
> Construye sobre la misma imagen y patrones de gate.

---

## 0. Contexto y propiedad objetivo

Gate de Fase 3 (decomposición §6.7 / §12.1, ADR-8): **aislamiento de la ejecución del runtime**,
fail-closed por **ADR-4** ("el OS debe garantizar aislamiento … o no arrancar el agente").

**Realidad del runtime (clave para el alcance):** `astromeshd` es `/opt/astromesh/venv/bin/python3`
corriendo el agente, **ya confinado por AppArmor** (Fase 3.2, deny-by-default): sólo ejecuta el
intérprete del venv, lee `/etc/astromesh`, escribe `/var/lib|/var/log/astromesh`, y abre TCP. El
perfil **no permite shell-out** (`/bin/sh` u otros exec), así que los "tools" del agente corren
**in-process** (Python), no como subprocesos no confiables separados. No existe hoy un proceso de
tool-execution aparte que sandboxear.

**Decisión de alcance (brainstorm):** el E-MVP del OS **endurece `astromeshd` in-place vía systemd**
a nivel de **syscalls + namespaces + privilegios**, complementando el confinamiento de **rutas** de
AppArmor. No se construye un wrapper `sandbox-exec` aparte (sería mecanismo sin consumidor: el
runtime es caja negra y no lo invocaría — YAGNI). El objetivo de **Landlock** (confinamiento de
rutas del FS) ya está cubierto por AppArmor 3.2, así que no se duplica.

**Por qué complementa y no reemplaza a AppArmor:** AppArmor restringe *qué rutas/recursos* toca el
proceso; seccomp restringe *qué syscalls* puede invocar; los namespaces/privilegios restringen *qué
puede crear o escalar*. Defensa en profundidad: un bug que evada una capa choca con la otra.

## 1. Objetivo y alcance

**Objetivo:** que `astromeshd` corra bajo un sandbox de syscalls+namespaces+privilegios aplicado por
systemd, y que **no arranque** si ese sandbox no puede activarse (fail-closed, ADR-4).

**En alcance (3.4):**
- Drop-in de endurecimiento en `astromeshd.service` (seccomp + restricciones de namespaces,
  familias de direcciones, privilegios, y protecciones de kernel).
- Self-check fail-closed (oneshot `Before=astromeshd`) que verifica que el sandbox está activo y
  prueba un **POSITIVE-BLOCK** (una operación peligrosa es efectivamente rechazada).
- Wiring fail-closed: `astromeshd` `Requires=` el self-check (no arranca si el sandbox falla).
- Gate de boot (KVM local + CI) que prueba marcadores + `astromeshd` healthy bajo el sandbox.

**Fuera de alcance (explícito):**
- Wrapper de sandbox por-tool / microVM (Firecracker/Kata) → fast-follow (ADR-8).
- Egress eBPF/XDP (§12.4) → gated por talento Rust+eBPF (R3/ADR-10), fuera de 3.4.
- `MemoryDenyWriteExecute=yes` → **diferido** (riesgo alto de romper extensiones C de Python;
  beneficio marginal sobre el resto del endurecimiento). Follow-up: validar en un discovery pass y
  añadir si el runtime no lo viola.
- Landlock explícito → su objetivo (confinamiento de rutas) ya lo cubre AppArmor 3.2.

**Invariante:** no romper gates de Fase 0/1/2/3.1/3.2/3.3 (health, A/B update, rollback, no-shell,
confinamiento, TPM-unseal). El endurecimiento es **aditivo** y no debe romper el arranque de
`astromeshd` ni el unseal de 3.3 (`EnvironmentFile=-/run/astromesh/env`). El plan re-corre rollback
(Fase 2), confine (3.2) y tpm (3.3) como regresión.

## 2. El drop-in de endurecimiento (`phase3/sandbox/30-sandbox.conf`)

`astromeshd.service.d/30-sandbox.conf`. Directivas y razón:

| Directiva | Efecto |
|---|---|
| `NoNewPrivileges=yes` | El proceso (y descendientes) no pueden ganar privilegios vía setuid/fscaps. Base de todo seccomp no privilegiado. |
| `SystemCallFilter=@system-service` | Allow-list curada de systemd para daemons (rara vez rompe Python). Todo lo demás se filtra. |
| `SystemCallErrorNumber=EPERM` | Una syscall filtrada devuelve **EPERM** en vez de matar el proceso con SIGSYS — el runtime caja-negra degrada en vez de crashear si toca algo no previsto. |
| `SystemCallArchitectures=native` | Bloquea ABIs no nativas (evita evadir el filtro vía x32/compat). |
| `RestrictNamespaces=yes` | Deniega crear namespaces nuevos (user/mount/net/…): el agente/tools no pueden montar su propio contenedor ni intentar escapes vía userns. |
| `RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX` | Sólo las familias que el runtime necesita (provider + health + sockets locales/DNS). Deniega `AF_NETLINK`, `AF_PACKET`, etc. |
| `RestrictRealtime=yes` | Sin scheduling de tiempo real (vector de DoS). |
| `RestrictSUIDSGID=yes` | No puede crear archivos setuid/setgid. |
| `LockPersonality=yes` | Fija la personality del kernel (evita emulaciones que cambian semántica de syscalls). |
| `ProtectKernelModules=yes` | No (des)cargar módulos. |
| `ProtectKernelTunables=yes` | `/proc/sys`, `/sys` read-only. |
| `ProtectKernelLogs=yes` | Sin acceso a `dmesg`/`/proc/kmsg`. |
| `ProtectClock=yes` | No cambiar el reloj del sistema. |
| `ProtectHostname=yes` | No cambiar hostname. |
| `ProtectControlGroups=yes` | `/sys/fs/cgroup` read-only. |
| `PrivateTmp=yes` | `/tmp` privado del servicio (aísla de otros). |

Notas de compatibilidad:
- **No** se usa `ProtectSystem=strict`/`ProtectHome` agresivo de más: el root ya es **verity
  read-only** (Fase 2) y AppArmor 3.2 ya restringe rutas; se evita redundancia que pueda chocar con
  el unseal de 3.3 a `/run` o el venv en `/opt`. (`PrivateTmp` sí, es barato y ortogonal.)
- El drop-in es **aditivo** al `AppArmorProfile=astromeshd` (3.2) y al `EnvironmentFile=-/run/astromesh/env`
  (3.3): `EnvironmentFile` lo lee systemd **antes** de aplicar el sandbox al payload, así que el
  unseal sigue funcionando.

**Wiring fail-closed (en el mismo drop-in o uno adyacente):**
`Requires=astromesh-sandbox-check.service` + `After=astromesh-sandbox-check.service` en
`astromeshd.service` → si el check falla, `astromeshd` **no arranca**.

## 3. El self-check fail-closed (`phase3/sandbox/astromesh-sandbox-check.{sh,service}`)

Oneshot, `Before=astromeshd.service`, que corre **bajo el mismo endurecimiento** (lleva las mismas
directivas seccomp/namespace que el drop-in, para poder inspeccionar su propio estado como proxy del
de astromeshd, que aún no arrancó).

El script:
1. **SECCOMP OK** — `/proc/self/status` muestra `Seccomp:` en modo filtro (valor `2`).
2. **NO-NEW-PRIVS OK** — `/proc/self/status` muestra `NoNewPrivs: 1`.
3. **POSITIVE-BLOCK OK** — intenta una operación que el sandbox debe denegar y confirma el rechazo:
   crear un namespace nuevo (`unshare --user --map-root-user true` o equivalente) → debe fallar con
   EPERM por `RestrictNamespaces`. (Análogo al POSITIVE-BLOCK de 3.2, que probaba una escritura
   fuera de política denegada por AppArmor.)
4. Emite `[sandbox] SANDBOX GATE OK` si todo pasa; cualquier fallo → `[sandbox] … FAILED` + exit≠0,
   lo que (por `Requires=`) impide el arranque de `astromeshd` y rojo en el gate.

Marcadores a consola (`StandardOutput=journal+console`): `[sandbox] SECCOMP OK`,
`[sandbox] NO-NEW-PRIVS OK`, `[sandbox] POSITIVE-BLOCK OK`, `[sandbox] SANDBOX GATE OK`.

---

## 4. Método de derivación del filtro (discovery → enforce, como 3.2)

1. **Discovery:** construir con el drop-in pero añadiendo `SystemCallLog=@system-service` invertido
   (o un filtro permisivo + `SystemCallLog`) para registrar a journald cualquier syscall que el
   runtime invoque **fuera** de `@system-service`, ejercitando startup + `/v1/health` + una query.
2. Si el pase de descubrimiento sale limpio (sin syscalls necesarias filtradas), **enforce** con
   `@system-service` tal cual. Si aparece alguna, añadir el grupo/syscall puntual y re-validar.
3. `SystemCallErrorNumber=EPERM` mantiene el daemon vivo aunque toque algo inesperado, evitando un
   crash-loop durante el ajuste.

---

## 5. El gate (`tests/boot/sandbox-and-assert.sh`)

Un solo boot (patrón de 3.1/3.2, KVM local / TCG CI):
1. Boot normal; el self-check emite marcadores.
2. El harness grepea `[sandbox] SANDBOX GATE OK` en la consola (incluye SECCOMP/NO-NEW-PRIVS/
   POSITIVE-BLOCK) y verifica `astromeshd` `/v1/health` 200 (prueba que el endurecimiento **no
   rompió** el runtime — la mitad "fail-closed no debe ser fail-open contra el propio agente").
3. Veredicto: `[sandbox] SANDBOX GATE PASSED`.

## 7. Criterios de done

- Local `dev-loop.sh sandbox` → `SANDBOX GATE PASSED` (marcadores SECCOMP/NO-NEW-PRIVS/POSITIVE-BLOCK
  + `astromeshd` healthy bajo el sandbox).
- CI `phase3-sandbox.yml` verde incluyendo `sandbox-gate`.
- Gates de Fase 0/2/3.1/3.2/3.3 siguen verdes (el drop-in es aditivo; no rompió health/update/
  rollback/no-shell/confine/unseal).
- Fail-closed demostrado: si el sandbox no puede aplicarse, `astromeshd` no arranca (vía
  `Requires=sandbox-check` + el POSITIVE-BLOCK).
- Spec roadmap de Fase 3 actualizado; 3.4 marcado done con referencia de run.

## 8. Riesgos

| Riesgo | Mitigación |
|---|---|
| `SystemCallFilter` demasiado estricto crashea el runtime | `@system-service` (daemon-safe) + `SystemCallErrorNumber=EPERM` (degrada, no mata) + discovery pass con `SystemCallLog`. |
| `RestrictAddressFamilies` rompe egress/DNS | Incluye `AF_INET/AF_INET6/AF_UNIX`; validar health (egress al provider) y resolución DNS en el gate. |
| `RestrictNamespaces` rompe algo que el runtime necesite | El runtime no crea namespaces (no hace shell-out bajo AppArmor); validar en el gate; el POSITIVE-BLOCK confirma que la denegación es efectiva. |
| `Requires=sandbox-check` tiene blast-radius (un bug del check tumba astromeshd y todos los gates) | Mantener el check simple/robusto; `set -euo pipefail`; probar primero en el gate de 3.4 antes de confiar en la regresión. |
| `MemoryDenyWriteExecute` rompería extensiones C de Python | **Fuera del MVP** (diferido); follow-up con discovery dedicado. |
| Interacción con 3.3 unseal (`EnvironmentFile=-/run/astromesh/env`) | systemd lee `EnvironmentFile` antes de aplicar el sandbox al payload; sin conflicto. Regresión tpm lo confirma. |
