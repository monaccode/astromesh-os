# Fase 4.2 — Malla de 2 nodos con mTLS (cierre R2 a nivel transporte) — Diseño

> **Estado:** Diseño aprobado en brainstorm (2026-06-09).
> **Tipo:** Spec de sub-proyecto (Fase 4, sub-proyecto **C** — segunda rebanada).
> **Precede:** Fase 4.1 (machine-config) + Fase 3 completa (esp. 3.3 TPM-seal, 3.6 self-owned keys).
> Construye sobre la misma imagen, el machine-config de 4.1 y los patrones de gate.

---

## 0. Contexto y propiedad objetivo

Gate de Fase 4 (decomposición): *el nodo joinea la malla solo con machine-config, sin SSH*. 4.1
entregó la configuración declarativa del nodo (perfil + identidad). 4.2 entrega la **malla**: dos
nodos forman cluster, pero **cerrando el gap de auth R2 antes de exponer la malla**.

**Realidad del runtime (clave para el alcance):** el runtime trae una **malla gossip** (config
`spec.mesh` en los perfiles `mesh-*`: `enabled`, `node_name`, `bind`, `seeds`, gossip/heartbeat). Los
endpoints `/v1/mesh/{state,join,leave,heartbeat,gossip,election}` viven en el **mismo** servidor HTTP
de la API (`:8000`) y **no tienen NINGUNA auth** (`MeshConfig` no tiene campos de TLS/cert/token). Ese
es exactamente el riesgo **R2**: "endpoints `/v1/mesh/*` sin auth; Bully election → split-brain". La
decomposición es enfática: **cerrar el gap de auth (mTLS + atestación TPM) ANTES de exponer cualquier
endpoint de malla.**

**Decisión de alcance (brainstorm):** el OS pone **mTLS por delante del plano de malla**, con una **CA
de cluster propia**. El runtime queda en **loopback** (su `/v1/mesh` nunca se expone directo); un
**sidecar mTLS** termina/origina el TLS entre nodos. Solo un nodo con un cert que encadena a la CA del
cluster participa; uno sin cert válido es rechazado en el handshake. La **key privada del nodo se sella
al TPM** (reusa 3.3) → atestación liviana (solo un boot íntegro presenta el cert).

**Fuera de alcance (explícito):**
- **Atestación remota por PCR-quote** (un peer verifica el quote TPM del que joinea antes de admitirlo)
  → **4.2b**. 4.2 da la atestación *liviana* (key sellada a TPM), no la remota.
- **Malla dinámica de N nodos con intercepción transparente** (nft/SO_ORIGINAL_DST del egress de
  malla) → follow-up. 4.2 es **2 nodos** con mapeo de peer semi-estático (cada nodo conoce a su único
  peer por el machine-config).
- Bully election / split-brain hardening (más allá de que la malla forme) → posterior.
- Provisioning multi-cloud de la CA → 4.5.

**Invariante:** no romper gates de Fase 0/1/2/3/4.1 (todos single-VM, sin malla). `mesh.enabled` solo
está en los perfiles `mesh-*`; sin un machine-config que seleccione un perfil `mesh-*`, no hay malla
(comportamiento de hoy). El sidecar/CA/seal solo se activan bajo perfil `mesh-*`. El plan re-corre
4.1 (machineconfig) y un gate de Fase 3 como regresión.

## 1. Objetivo y alcance

**Objetivo:** que dos nodos formen una malla cuyo plano de control viaja **solo sobre mTLS** entre
nodos autenticados por una CA de cluster propia (key del nodo sellada a TPM), y que un nodo sin cert
válido **no** pueda participar — todo configurado por machine-config, sin SSH.

**En alcance (4.2):**
- CA de cluster propia (TEST committeada) + emisión por-nodo del cert (CN=`node_id`) en el primer boot,
  con la **key privada sellada al TPM**.
- Sidecar mTLS: server (mTLS in → runtime loopback) + cliente saliente (mapeo semi-estático de 2 nodos).
- Runtime en loopback (`mesh.bind=127.0.0.1:8000`); el OS confina la red.
- Harness de 2 VMs unidas por `socket netdev` de QEMU; IP estática + rol vía machine-config.
- Gate: positivo (`cluster_size=2` en ambos) + negativo R2 (cliente sin cert rechazado en el handshake).

## 2. Trust: CA de cluster + cert por-nodo sellado a TPM

- **CA del cluster:** `phase4/mesh/ca.crt` + `phase4/mesh/ca.key` — un keypair **TEST committeado**
  (mismo patrón/caveat que las SB keys de 3.6: INSEGURO, dev/CI; prod usa una CA offline/KMS y no
  committea la key). `ca.crt` es el **trust anchor** horneado en la imagen.
- **Cert por-nodo (primer boot):** un oneshot genera un keypair, se auto-emite un cert `CN=<node_id>`
  (el `node_id` viene del machine-config de 4.1) firmado por `ca.key`, y **sella la key privada al TPM**
  reusando el mecanismo de 3.3 (seal a PCR 11+12; unseal a tmpfs en cada boot íntegro). Idempotente:
  no re-emite si ya hay cert+blob.
- **Modelo de confianza (MVP, TEST):** la `ca.key` está horneada → cualquier nodo de la imagen puede
  auto-emitir su cert. El boundary que cierra R2 en 4.2: un nodo **sin** cert firmado por *esta* CA (o
  con cert de otra CA / sin cert) es rechazado. La atestación de *qué imagen/boot* emitió el cert es
  la *liviana* (key sellada a TPM); la remota (PCR-quote) es 4.2b. **Prod:** CA key fuera de la imagen
  (provisioning emite el cert tras atestación) — documentado en el README.

## 3. Sidecar mTLS (el runtime no habla TLS)

El runtime sirve `/v1/mesh` en HTTP plano en `:8000`. El OS lo confina a loopback y mete un sidecar:

- **Server sidecar** (`phase4/mesh/mesh-tls-server.*`, p.ej. `stunnel`/`ghostunnel` — el plan elige
  tras confirmar qué hay/empaqueta en la imagen mínima): escucha el **puerto de malla externo**
  (`:8443`) con TLS y **verifica el cert del cliente contra `ca.crt`** (mTLS); forward a
  `127.0.0.1:8000` (runtime). Sin cert válido → handshake rechazado, el runtime nunca se toca.
- **Client saliente:** las conexiones de malla salientes del runtime (a sus seeds/peers) deben
  presentarse con el cert del nodo. **[Simplificación MVP — 2 nodos]:** cada nodo mapea un proxy
  cliente local (`127.0.0.1:<p>` → mTLS → `<peer-ip>:8443`) a su **único peer** conocido por el
  machine-config; el `seed`/advertise del runtime apunta al proxy cliente local. La intercepción
  transparente para N peers dinámicos queda como follow-up.
- **Runtime:** `mesh.bind=127.0.0.1:8000` (loopback) en el perfil `mesh-*` o por override de la
  machine-config; el plan confirma cómo el runtime advierte su dirección de malla y lo alinea con el
  sidecar.

## 4. Harness (2 VMs hablándose)

- `slirp` (`-nic user`) **aísla** los guests entre sí. El gate une 2 VMs con un **`-netdev socket`**
  de QEMU (un VM `listen=`, el otro `connect=`) → un segmento L2 entre ambas. Cada VM mantiene además
  su `-nic user` con `hostfwd` para que el harness lea `/v1/health` y los markers desde el host.
- **IP estática + rol por machine-config:** el machine-config de cada nodo lleva (extendiendo el
  formato de 4.1, que ignora campos desconocidos hacia adelante) su **IP de malla estática** y el
  **peer** (gateway↔worker); un oneshot la aplica al NIC del segmento socket y arma el `/etc/hosts`
  (o el mapeo de seeds) para que `seeds: [http://gateway:8000]` del perfil resuelva al peer.
- Boot gateway: machine-config `profile=mesh-gateway, node_id=gateway, mesh_ip=…, peer=worker@…`.
  Boot worker: `profile=mesh-worker, node_id=worker, mesh_ip=…, peer=gateway@…, seed=gateway`.

## 5. El gate (`tests/boot/mesh-mtls-and-assert.sh`)

Dos VMs del mismo disco, unidas por `socket netdev`, con machine-configs de rol distinto vía SMBIOS:

1. **Positivo (cluster forma):** ambos nodos sellan/des-sellan su cert, levantan el sidecar mTLS, y la
   malla forma. El harness consulta `/v1/mesh/state` (vía el loopback de cada nodo por su hostfwd) y
   verifica `cluster_size == 2` en **ambos**. Markers: `[mesh] CERT-SEALED OK`, `[mesh] CLUSTER-FORMED size=2 OK`.
2. **Negativo (R2 — auth):** un cliente **sin cert** (o con un cert de **otra CA**, generado en el
   harness) intenta `https://<node-ip>:8443/v1/mesh/state` → el server sidecar **rechaza el handshake**
   (no llega al runtime). Marker `[mesh] UNAUTH-REJECTED OK`. (Prueba que `/v1/mesh` no está expuesto
   sin auth — el cierre R2.)
3. Veredicto: `[mesh] MESH MTLS GATE PASSED`.

> El negativo prueba el boundary de transporte (cert válido requerido). El positivo prueba que dos
> nodos **atestados-liviano** (key TPM-sellada) forman cluster. Juntos = "la malla solo entre nodos
> autenticados".

## 7. Criterios de done

- Local `dev-loop.sh mesh` → `MESH MTLS GATE PASSED` (positivo `cluster_size=2` en ambos nodos;
  negativo: cliente sin/mal cert rechazado en el handshake mTLS).
- CI `phase4-mesh.yml` verde incluyendo `mesh-mtls-gate`.
- Gates de Fase 0/2/3/4.1 siguen verdes (mesh solo bajo perfil `mesh-*`; single-VM intacto).
- El runtime `/v1/mesh` **no** se expone sin auth: solo a través del sidecar mTLS (runtime en loopback).
- La key del cert por-nodo se sella al TPM (no queda plaintext persistente).
- Roadmap de Fase 4 actualizado; 4.2 marcado done con referencia de run.

## 8. Riesgos

| Riesgo | Mitigación |
|---|---|
| 2 VMs no se ven (slirp aísla) | `socket netdev` de QEMU (L2 entre las dos) + IP estática por machine-config; el plan valida con un ping/curl entre nodos antes del mesh. |
| mTLS sobre gossip dinámico (addressing peer→sidecar) es complejo | **MVP de 2 nodos con mapeo semi-estático** (cada nodo conoce su único peer por machine-config); intercepción transparente (N nodos) → follow-up documentado. |
| El runtime advierte una dirección que no pasa por el sidecar | El plan confirma cómo el runtime arma su `bind`/advertise y alinea seeds + advertise con los puertos del sidecar (loopback + `:8443`); valida con `cluster_size=2`. |
| El sidecar TLS no está en la imagen mínima | El plan elige el tool tras un discovery (`stunnel4` está en Debian; alternativa `ghostunnel` como binario, u `openssl s_server`/`socat` para el MVP) y lo añade a `Packages=`/instala. |
| El seal del cert reusa 3.3 pero choca con el unseal del provider key | Ambos usan tpm2-tools con sesiones de policy PCR 11+12 (3.3); blobs separados (`/var/lib/astromesh/secrets/mesh.*`); el plan re-corre el gate `tpm` como regresión. |
| `mesh.bind=loopback` rompe el descubrimiento de peers | Validar en el gate (`cluster_size=2`); si el runtime exige bind no-loopback para advertir, el sidecar server escucha el puerto real y el runtime advierte esa dirección, no la loopback. |
| Romper gates single-VM de 0/2/3/4.1 | mesh gated por perfil `mesh-*`; sin él, units mesh no-op (guard) y el nodo bootea como hoy; regresión de 4.1 + un gate de Fase 3. |
| CA key horneada (TEST) malinterpretada como segura | README con el caveat (como 3.6); prod usa CA offline + emisión tras atestación (4.2b). |
