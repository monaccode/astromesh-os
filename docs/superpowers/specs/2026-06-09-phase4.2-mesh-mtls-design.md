# Fase 4.2 — Malla de 2 nodos con IPsec + CA de cluster (cierre R2 a nivel transporte) — Diseño

> **Estado:** Diseño aprobado en brainstorm (2026-06-09). **Revisado tras discovery** (ver §0.1): el
> sidecar mTLS app-layer es inviable (el runtime advierte `http://{bind}`), así que la auth mutua va a
> **L3 con IPsec (strongSwan) + la CA de cluster** — mismo modelo de confianza (CA + cert por-nodo, key
> sellada a TPM), a nivel de red.
> **Tipo:** Spec de sub-proyecto (Fase 4, sub-proyecto **C** — segunda rebanada).
> **Precede:** Fase 4.1 (machine-config) + Fase 3 completa (esp. 3.3 TPM-seal, 3.6 self-owned keys).

---

## 0. Contexto y propiedad objetivo

Gate de Fase 4: *el nodo joinea la malla solo con machine-config, sin SSH*. 4.1 entregó la config
declarativa del nodo (perfil + identidad). 4.2 entrega la **malla**: dos nodos forman cluster
**cerrando el gap de auth R2 antes de exponer la malla**.

**Realidad del runtime (clave para el alcance):** el runtime trae una **malla gossip** (config
`spec.mesh` en los perfiles `mesh-*`). Los endpoints `/v1/mesh/{state,join,leave,heartbeat,gossip,
election}` viven en el **mismo** servidor HTTP de la API (`:8000`) y **no tienen NINGUNA auth**
(`MeshConfig` no trae TLS/cert/token). Ese es el riesgo **R2**. La decomposición es enfática: cerrar
el gap de auth **antes** de exponer cualquier endpoint de malla.

### 0.1 Por qué IPsec/L3 y no un sidecar mTLS app-layer (discovery)

El borrador asumía un sidecar mTLS con el runtime en loopback. **Inviable:** el mesh manager advierte
a sus peers `url = f"http://{self._config.bind}"` (`manager.py:37`) — **`advertise == bind`**, sin
campo de dirección externa separada, y no podemos parchear el `.deb` pineado. Si el runtime bindea
loopback advierte una URL loopback (los peers no lo alcanzan); si bindea su IP de malla, escucha ahí
en HTTP plano y no hay puerto/dirección libre donde meter un sidecar mTLS. Conclusión: la auth mutua
**tiene que ir debajo del runtime, a L3**. El runtime bindea/advierte su IP de malla (HTTP plano sobre
la interfaz); el tráfico nodo-a-nodo se autentica+cifra con **IPsec (IKEv2 + certs X.509 de la CA de
cluster)**. Un nodo sin cert de la CA **no levanta el SA IPsec** → no alcanza a ningún peer → rechazado.
Mismo modelo de confianza que el elegido (CA propia + cert por-nodo + key sellada a TPM), a L3.

**Decisión de alcance (brainstorm + revisión):** IPsec IKEv2 con auth mutua de cert (CA de cluster
propia), key del nodo sellada a TPM. El runtime sin cambios, sobre la interfaz protegida por IPsec.

**Fuera de alcance (explícito):**
- **Atestación remota por PCR-quote** (un peer verifica el quote TPM del que joinea) → **4.2b**. 4.2
  da atestación *liviana* (key del cert sellada a TPM), no la remota.
- **Malla dinámica de N nodos** (descubrimiento + SAs IPsec dinámicos por peer) → follow-up. 4.2 son
  **2 nodos** con política IPsec semi-estática (cada nodo conoce el subnet/peer por machine-config).
- Bully election / split-brain hardening → posterior. Provisioning multi-cloud de la CA → 4.5.

**Invariante:** no romper gates de Fase 0/1/2/3/4.1 (todos single-VM, sin malla). `mesh.enabled` solo
en perfiles `mesh-*`; sin un machine-config `mesh-*`, no hay malla ni IPsec (comportamiento de hoy).
El plan re-corre 4.1 (machineconfig) y un gate de Fase 3 como regresión.

## 1. Objetivo y alcance

**Objetivo:** que dos nodos formen una malla cuyo tráfico nodo-a-nodo viaja **solo sobre IPsec** con
auth mutua de cert encadenado a una CA de cluster propia (key del nodo sellada a TPM), y que un nodo
sin cert válido **no** pueda alcanzar a ningún peer — todo por machine-config, sin SSH.

**En alcance (4.2):**
- CA de cluster propia (TEST committeada) + emisión por-nodo del cert (CN=`node_id`) en el primer boot,
  con la **key privada sellada al TPM**.
- strongSwan: IKEv2, auth mutua de cert (`leftcert`/`rightca`), SA ESP entre los 2 nodos.
- Runtime sin cambios; `mesh.bind` = la IP de malla del nodo (advertise==bind funciona).
- Harness de 2 VMs unidas por `socket netdev` de QEMU; IP de malla + rol vía machine-config.
- Gate: positivo (`cluster_size==2` en ambos) + negativo R2 (nodo sin cert no levanta SA → no joinea).

## 2. Trust: CA de cluster + cert por-nodo sellado a TPM

- **CA del cluster:** `phase4/mesh/ca.crt` + `phase4/mesh/ca.key` — keypair **TEST committeado** (mismo
  patrón/caveat que las SB keys de 3.6: INSEGURO, dev/CI; prod usa CA offline/KMS, no committea la key).
  `ca.crt` = trust anchor horneado.
- **Cert por-nodo (primer boot):** un oneshot genera un keypair, se auto-emite un cert `CN=<node_id>`
  (`node_id` del machine-config de 4.1) firmado por `ca.key`, con `subjectAltName` = la IP de malla
  (IKEv2 valida el ID contra el SAN), y **sella la key privada al TPM** reusando 3.3 (seal a PCR 11+12;
  unseal a tmpfs cada boot íntegro). Idempotente.
- **Modelo de confianza (MVP, TEST):** `ca.key` horneada → cualquier nodo de la imagen auto-emite su
  cert. El boundary R2 que cierra 4.2: un nodo **sin** cert de *esta* CA no completa IKEv2 → sin SA →
  sin acceso a la malla. La atestación *de qué boot* emitió el cert es la liviana (key sellada a TPM);
  la remota (PCR-quote) es 4.2b. **Prod:** CA key fuera de la imagen (provisioning emite tras
  atestación) — documentado.

## 3. IPsec L3 (strongSwan) — el runtime no cambia

- **strongSwan** (`strongswan`/`swanctl`, paquete trixie `6.0.1`; el kernel cloud de la imagen trae
  los módulos `esp4`/`xfrm_user`/`xfrm_algo`/`af_key` — verificado). `swanctl.conf` con una conexión
  IKEv2: `local.auth=pubkey` con el cert del nodo (key des-sellada del TPM), `remote.auth=pubkey` con
  `remote.cacerts = ca.crt` (acepta cualquier cert firmado por la CA), `children` = SA ESP que protege
  el subnet de malla (`<mesh-subnet>` entre los 2 nodos).
- **Política:** el tráfico hacia la IP de malla del peer (`<mesh-subnet>`, p.ej. `10.77.0.0/24`) exige
  el SA IPsec; sin SA (peer sin cert) el paquete se dropea → el peer es inalcanzable. El runtime
  (`mesh.bind=<mesh-ip>:8000`, HTTP plano) viaja **dentro** del SA, transparente.
- **Runtime:** perfil `mesh-*` con `mesh.bind=<mesh-ip>:8000` (la IP de malla, no loopback — necesario
  porque advertise==bind); `seeds` apuntan a la IP de malla del peer. El plan fija el subnet/IPs.

## 4. Harness (2 VMs hablándose)

- `slirp` (`-nic user`) aísla los guests → el gate une 2 VMs con un **`-netdev socket`** de QEMU (una
  `listen=`, otra `connect=`) → segmento L2 entre ambas, sobre el que corre IPsec. Cada VM mantiene su
  `-nic user` con `hostfwd` para que el harness lea `/v1/health` + markers desde el host.
- **IP de malla + rol por machine-config:** el machine-config de cada nodo lleva (extendiendo 4.1, que
  ignora campos desconocidos) su **IP de malla estática** y el **peer**; un oneshot la aplica al NIC del
  segmento socket y arma el mapeo de seeds (`/etc/hosts`) para que el `seeds` del perfil resuelva al
  peer.
- Boot gateway: `profile=mesh-gateway, node_id=gateway, mesh_ip=10.77.0.1, peer=10.77.0.2`.
  Boot worker: `profile=mesh-worker, node_id=worker, mesh_ip=10.77.0.2, peer=10.77.0.1, seed=gateway`.

## 5. El gate (`tests/boot/mesh-ipsec-and-assert.sh`)

Dos VMs del mismo disco, unidas por `socket netdev`, con machine-configs de rol distinto vía SMBIOS:

1. **Positivo (cluster forma sobre IPsec):** ambos nodos des-sellan su cert, levantan el SA IPsec
   (`swanctl --list-sas` muestra `ESTABLISHED`), la malla forma. El harness consulta `/v1/mesh/state`
   (vía hostfwd de cada nodo) y verifica **`len(nodes)==2`** en ambos. Markers: `[mesh] CERT-SEALED OK`,
   `[mesh] IPSEC-SA-UP OK`, `[mesh] CLUSTER-FORMED size=2 OK`.
2. **Negativo (R2 — auth):** una tercera "VM rogue" (o el mismo harness) con un cert **de otra CA** (o
   sin cert) intenta el SA IPsec contra un nodo → IKEv2 **falla** (cert no encadena a `ca.crt`) → sin
   SA → no alcanza `<mesh-ip>:8000` (connect dropeado) → no joinea. Marker `[mesh] UNAUTH-REJECTED OK`.
3. Veredicto: `[mesh] MESH IPSEC GATE PASSED`.

> El negativo prueba el boundary L3 (cert de la CA requerido para el SA). El positivo prueba que dos
> nodos atestados-liviano (key TPM-sellada) forman cluster sobre IPsec. Juntos = "la malla solo entre
> nodos autenticados".

- Local `dev-loop.sh mesh` → `MESH IPSEC GATE PASSED` (positivo `cluster_size=2` + SA `ESTABLISHED`;
  negativo: nodo sin/mal cert no levanta el SA → no joinea).
- CI `phase4-mesh.yml` verde incluyendo `mesh-ipsec-gate`.
- Gates de Fase 0/2/3/4.1 siguen verdes (mesh+IPsec solo bajo perfil `mesh-*`; single-VM intacto).
- El runtime `/v1/mesh` solo viaja dentro del SA IPsec; un nodo sin cert de la CA no lo alcanza.
- La key del cert por-nodo se sella al TPM (sin plaintext persistente).
- Roadmap de Fase 4 actualizado; 4.2 marcado done con referencia de run.

## 8. Riesgos

| Riesgo | Mitigación |
|---|---|
| 2 VMs no se ven (slirp aísla) | `socket netdev` de QEMU (L2) + IP de malla estática por machine-config; el plan valida ping entre nodos (post-SA) antes del mesh. |
| El kernel cloud no trae IPsec/ESP | **Verificado:** `esp4/xfrm_user/xfrm_algo/af_key/ah4` están en `/lib/modules` del kernel `6.12.90-cloud`. El unit hace `modprobe esp4` y falla-claro si ausente. |
| `mesh.bind` debe ser la IP de malla (no loopback) → `/v1/mesh` "expuesto" sobre la interfaz | La interfaz solo lleva tráfico **dentro del SA IPsec**; la política dropea lo no-protegido hacia el mesh-subnet. El runtime nunca recibe tráfico no autenticado de malla. (El `:8000` de la API local sigue por loopback/hostfwd para el harness; la política IPsec aplica al mesh-subnet, no a slirp.) |
| swanctl/charon finicky bajo el sandbox/seccomp/AppArmor de 3.x | strongSwan corre en sus **propios** units (no bajo el confinamiento de astromeshd); el plan valida `swanctl --list-sas`. |
| El seal del cert reusa 3.3 y choca con el unseal del provider key | tpm2-tools con sesión policy PCR 11+12 (3.3); blobs separados (`/var/lib/astromesh/secrets/mesh.*`); regresión del gate `tpm`. |
| IKEv2 valida el ID del peer | cert con `subjectAltName`=mesh_ip; `swanctl.conf` usa `remote.id`/`rightid` acorde; el plan lo fija y valida con el SA `ESTABLISHED`. |
| Romper gates single-VM 0/2/3/4.1 | mesh+IPsec gated por perfil `mesh-*`; sin él, units no-op (guard) y el nodo bootea como hoy; regresión de 4.1 + un gate de Fase 3. |
| CA key horneada (TEST) malinterpretada como segura | README con caveat (como 3.6); prod = CA offline + emisión tras atestación (4.2b). |
