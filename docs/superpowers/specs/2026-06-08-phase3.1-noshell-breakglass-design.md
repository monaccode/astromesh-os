## 1. Objetivo y alcance

**Objetivo:** eliminar la superficie de **shell interactivo de operador** por defecto
(anti-objetivo del spec: "No shell/SSH interactivo por default"), conservando una vía de
recuperación **break-glass** controlada: shell root SOLO en la consola física/serial y SOLO
con una credencial provisionada.

**En alcance (3.1):** login shells (getty/SSH) y el drop a `rescue`/`emergency`.

**Fuera de alcance (explícito):**
- Impedir que `astromeshd`/agentes/tools lancen shells → eso es **sandboxing (3.4)**.
- Sellar la credencial a TPM → **3.3** (3.1 deja el upgrade-path listo).
- Bloquear edición de cmdline en el bootloader → **3.6 / Secure Boot**.
- Editar archivos en recuperación: el root es verity-inmutable (Fase 2); break-glass da un
  shell de **diagnóstico**, no de edición del root.

**Invariante:** 3.1 NO debe romper los gates de Fase 0/2 (health, A/B update, rollback).
Esos harnesses verifican marcadores de consola y `/v1/health`, no el prompt de login, así
que enmascarar getty es seguro para ellos. El plan lo valida re-corriendo el rollback gate.

## 2. Mecanismo no-shell (imagen por defecto)

En `mkosi.postinst.chroot` (bloque nuevo de Fase 3):

- **Enmascarar** las units de login de consola:
  `serial-getty@.service`, `getty@.service`, `console-getty.service`, `autovt@.service`,
  y `getty.target`. Sin prompt de login en ninguna consola en el boot normal a
  `astromesh-os.target` (que aún `Requires=multi-user.target`, pero getty queda enmascarado).
- **SSH fuera:** `openssh-server` no está en `Packages=` (ya es el caso). El self-check
  (§4) **falla** si alguna vez aparece instalado, como red de seguridad anti-regresión.
- **Rescue fail-closed por defecto:** `RootPassword=hashed:!` (root bloqueado) se mantiene
  como default de `mkosi.conf`. `sulogin` moderno **rehúsa** abrir shell para una cuenta
  bloqueada sin `SYSTEMD_SULOGIN_FORCE=1` (que NO seteamos). Así, un fallo de boot que caiga
  a `emergency`/`rescue` **no** entrega un shell sin autenticar.

## 3. Mecanismo break-glass

- **Credencial:** variable de build/provision `ASTROMESH_BREAKGLASS_HASH` (hash crypt(5),
  p.ej. `$y$…` de `mkpasswd`/`openssl passwd`). Se agrega a `[Build] Environment=` en
  `mkosi.conf` (pass-through como `PHASE0_MODE`). Cuando está presente, postinst la setea
  como **hash de password de root** (`usermod`/`chpasswd -e`, o editar `/etc/shadow`).
  Como getty está enmascarado y SSH ausente, esa credencial **sólo** es verificable por
  `sulogin` en la consola física/serial.
  - No hay hash horneado por default: el gate (`dev-loop.sh noshell` / job `noshell-gate`)
    **pasa explícitamente** un hash dev conocido (password `breakglass`) para poder
    autenticar el login interactivo. En prod se inyecta el hash real por el secreto del runner.
  - Si la variable está vacía → root queda bloqueado (`!`) → break-glass deshabilitado
    (fail-closed). El self-check lo reporta `BREAK-GLASS=disabled`.
- **Trigger (operador):** en la consola, interrumpir el menú de systemd-boot, agregar
  `systemd.unit=rescue.target` (o `emergency`) al cmdline del entry, bootear →
  `rescue.service` corre `sulogin` → ingresar la credencial → shell root.
- **Runbook:** `phase3/BREAK-GLASS.md` documenta el procedimiento exacto, su naturaleza
  auditada (queda en journal/consola) y las dependencias futuras (3.3 sella la credencial;
  3.6 mueve el trigger a un entry de boot medido cuando Secure Boot bloquee la edición de
  cmdline).
- **loader.conf:** para que el menú sea interrumpible en consola serial, `timeout` > 0 y
  `editor yes` (default). Nota: 3.6 endurecerá esto.

## 4. Self-check de hardening (marcador de boot)

`phase3/astromesh-hardening-check.{sh,service}` — oneshot, espejo de
`phase2/immutability-check.*`, `WantedBy=multi-user.target`, salida a `journal+console`.
Asevera y loguea, fail-closed (exit ≠ 0 si algo no cumple):

- getty units enmascaradas (`systemctl is-enabled …` == `masked`).
- `openssh-server` NO instalado (`dpkg-query`).
- estado break-glass: root con hash válido → `BREAK-GLASS=configured`; bloqueado →
  `BREAK-GLASS=disabled`.
- Marcador final a consola: `[hardening] NO-SHELL OK` (+ línea `BREAK-GLASS=…`).

El harness del gate grepea `NO-SHELL OK` para la mitad no-shell.

## 5. Gate — interactivo completo (gold standard)

`tests/boot/noshell-and-assert.sh`, dos aserciones:

1. **No-shell (barato):** bootear normal, esperar `[hardening] NO-SHELL OK` en la consola
   serial. Falla si no aparece, o si aparece un shell/login utilizable.
2. **Break-glass (end-to-end):** un driver expect/pexpect (Python; el repo ya usa Python
   para el stub) maneja la consola serial de QEMU:
   - esperar el menú de systemd-boot, enviar las teclas para editar el entry y agregar
     ` systemd.unit=rescue.target`, Enter;
   - esperar el prompt de `sulogin` ("Press Enter for maintenance" / "root password:");
   - enviar la credencial dev (`breakglass`);
   - esperar el shell root y ejecutar `id`; **assert** `uid=0`;
   - además: un boot de control SIN credencial (o credencial errónea) **no** entrega shell.

`tests/local/dev-loop.sh`: target `noshell` (build imagen + correr el gate en WSL2+KVM).
`.github/workflows`: job `noshell-gate` (TCG) — mismo script, KVM local ≈ CI.

## 7. Criterios de done

- Boot normal: sin login interactivo en ninguna consola; `NO-SHELL OK` en consola.
- Break-glass: `dev-loop.sh noshell` prueba end-to-end el shell root por `rescue` + credencial
  (`uid=0`), y que sin credencial no hay shell.
- CI `noshell-gate` verde (TCG).
- Los gates de Fase 0/2 (health, update, rollback) siguen verdes — no-shell no los rompió.
- STATUS/decomposición actualizados; 3.1 marcado done con referencia de run.

## 8. Riesgos

| Riesgo | Mitigación |
|---|---|
| Manejar el menú de systemd-boot por serial es frágil (timing de teclas) | `timeout` holgado en `loader.conf`; driver pexpect con esperas por patrón, no por tiempo |
| `sulogin` con root bloqueado podría, mal configurado, abrir shell sin password | NO setear `SYSTEMD_SULOGIN_FORCE`; el self-check verifica el estado de la credencial |
| Enmascarar getty rompe algún harness de Fase 2 | Esos harnesses no usan login; el plan re-corre el rollback gate como regresión |
| Credencial dev hardcodeada filtra a prod | Default sólo si la env está vacía; prod inyecta el hash real; runbook lo advierte |
