# Fase 3.2 — MAC enforcing (AppArmor para astromeshd) — Diseño

> **Estado:** Diseño aprobado en brainstorm (2026-06-08).
> **Tipo:** Spec de sub-proyecto (Fase 3, sub-proyecto D parcial). Alimenta un plan (writing-plans).
> **Precede:** Fase 3.1 (no-shell + break-glass) cerrada. Construye sobre la misma imagen.

---

## 0. Contexto y decisión de MAC

El roadmap de Fase 3 (decomposición §3, sub-proyecto D) pide **"SELinux enforcing"**. En el
brainstorm se decidió implementar el MAC con **AppArmor** en vez de SELinux, porque para
**este stack** es la opción correcta:

- **Debian-native:** AppArmor es el MAC por default de Debian (compilado y activo); SELinux es
  opt-in vía `refpolicy`/`selinux-policy-default`, second-class y menos mantenido en Debian.
- **Encaja con verity:** SELinux etiqueta vía xattrs `security.selinux` que deben hornearse en
  build (`setfiles`) y no se pueden re-etiquetar en runtime sobre un root verity read-only.
  AppArmor es **path-based** (sin xattrs/labels) → encaja natural con la imagen inmutable y el
  `/etc` stateless.
- **Mismo goal:** sub-proyecto D pide "agente confinado, MAC enforcing, sin degradar". AppArmor
  lo cumple para astromeshd con mucho menos esfuerzo.

3.2 satisface el **goal** de D (confinamiento MAC enforcing de astromeshd), desviándose del
texto literal "SELinux". Si más adelante aparece un requisito de compliance SELinux específico,
se reabre como sub-proyecto aparte.

Estado actual: **ningún MAC activo** en la imagen (no hay config selinux ni apparmor). El kernel
cloud de Debian (`linux-image-cloud-amd64`) trae AppArmor como LSM; falta el userspace + perfil.

---

## 1. Objetivo y alcance

**Objetivo:** confinar **astromeshd** con un perfil AppArmor en modo **enforce** (deny-by-default),
sin denials en operación normal (health 200 + una query de agente), y probar que el enforce
realmente bloquea acciones fuera de política.

**En alcance (3.2):** el footprint del **daemon** astromeshd (qué lee/escribe/ejecuta/red).

**Fuera de alcance (explícito):**
- Confinar otros servicios (updater A/B, boot-check, stub, hardening-check) — quedan sin perfil.
  El updater es privilegiado por naturaleza (escribe particiones); confinarlo es 3.x posterior.
- Sandbox de **ejecución de tools** del agente (seccomp+Landlock+namespaces) → **3.4**. 3.2 confina
  el proceso del daemon, NO las tool calls que el agente dispare.
- SELinux (decisión arriba).

**Invariante:** 3.2 no debe romper los gates de Fase 0/1/2/3.1 (health, A/B update, rollback,
no-shell). El plan re-corre el rollback gate y el phase0 gate como regresión si cambian archivos
compartidos (mkosi.conf/postinst).

## 2. El perfil AppArmor (`/etc/apparmor.d/astromeshd`)

Perfil **nombrado** (no path-attached), deny-by-default, en enforce. Se refina empíricamente en
complain mode (§4); el contenido inicial cubre lo que astromeshd necesita:

- `#include <abstractions/base>` `#include <abstractions/python>` `#include <abstractions/nameservice>`
- Ejecutar el intérprete del venv: `/opt/astromesh/venv/bin/python3 ix,` y leer su árbol:
  `/opt/astromesh/venv/** r,`
- Config read-only: `/etc/astromesh/** r,` (agents, `.env`, providers)
- Estado escribible (las ÚNICAS rutas de escritura permitidas):
  `/var/lib/astromesh/** rwk,` `/var/log/astromesh/** rwk,`
- Red: `network inet stream,` `network inet6 stream,` (bind `:8000` + egress al provider).
  Sin capabilities (corre como usuario `astromesh`, puerto > 1024).
- Lecturas mínimas de runtime que las abstractions no cubran (`/proc/sys/...`, `/sys/...`) se
  agregan según los denials reales del complain pass — NO se pre-aprueban a ciegas.

El perfil se attacha al servicio vía drop-in systemd (§3), así la transición no depende del path
exacto del exec (que es el python del venv).

## 3. Wiring (encaje con verity-immutable)

En `mkosi.conf` Packages: `apparmor`, `apparmor-utils` (provee `aa-status`, `aa-exec`, `aa-enabled`,
y el tooling de desarrollo del perfil).

En `mkosi.postinst.chroot` (bloque Fase 3.2):
- Instalar el perfil `phase3/apparmor/astromeshd` → `/etc/apparmor.d/astromeshd`.
- Instalar el drop-in `phase3/apparmor/20-apparmor.conf` → `/etc/systemd/system/astromeshd.service.d/`
  con `AppArmorProfile=astromeshd` (enforce; named-profile attach).
- `systemctl enable apparmor.service` (carga los perfiles de `/etc/apparmor.d/` en boot).
- Redirigir la caché del parser a `/var` (el root `/etc` es read-only verity): apparmor recompila
  el perfil en boot si no hay caché escribible; apuntar la caché a un dir bajo `/var` (tmpfiles)
  o aceptar la recompilación en boot (sin caché). Decisión de implementación en el plan.
- LSM: verificar en build/boot que AppArmor está activo (`aa-enabled` / `/sys/module/apparmor/parameters/enabled`
  == `Y`). Si el kernel cloud no lo trae activo por default, agregar `apparmor=1 security=apparmor`
  a `KernelCommandLine` en `mkosi.conf`.

Notas verity: el perfil vive en `/etc/apparmor.d/` (horneado, read-only) — apparmor lo LEE y lo
carga al kernel; el read-only no estorba (no se escribe `/etc`). La caché es lo único que querría
escribir, y va a `/var`.

## 4. Enfoque de desarrollo (complain → enforce)

Iterativo, como 3.1:
1. Shipear el perfil en **complain** mode (`AppArmorProfile=-astromeshd` no; complain se setea con
   el perfil en modo complain — flag `flags=(complain)` en el perfil, o `aa-complain` en build).
2. Bootear, ejercitar los paths normales (health + una query de agente).
3. Recolectar las líneas de audit `apparmor="ALLOWED"`/`apparmor="DENIED"` (en complain todo se
   permite pero se loguea lo que enforce bloquearía).
4. Refinar las reglas allow del perfil con eso.
5. Flipear a **enforce**, re-correr, confirmar **cero denials** en operación normal.

El `dev-loop.sh` recibe un target `confine` para correr este loop local (WSL2+KVM).

## 5. El gate (`tests/boot/confine-and-assert.sh`)

Cuatro aserciones, sobre una imagen booteada con KVM (local) / TCG (CI):

1. **Funcional:** `/v1/health` 200 **y** una query al agente `phase0-smoke` devuelve respuesta
   no vacía (reusar la lógica de `tests/boot/run-and-assert.sh`). El confinamiento no rompió el daemon.
2. **Confinado:** con el PID del servicio (`systemctl show -p MainPID --value astromeshd`),
   `/proc/<MainPID>/attr/current` == `astromeshd (enforce)` y `aa-status` lista el perfil en
   enforce — **no** `unconfined`.
3. **Sin denials:** ningún `apparmor="DENIED"` para el perfil `astromeshd` en el journal/dmesg
   durante la operación normal.
4. **Enforcement positivo:** `aa-exec -p astromeshd -- <acción fuera de política>` (p.ej. escribir
   fuera de `/var/lib/astromesh`, o leer una ruta no permitida) **falla** con permission denied **y**
   emite un `apparmor="DENIED"`. Prueba que enforce realmente bloquea (no es complain disfrazado).

El test corre dentro del guest (necesita `aa-exec`/journal del propio sistema): el harness arranca
QEMU, espera health, dispara la query desde el host, y para (2)-(4) ejecuta los checks vía un
pequeño oneshot/`systemd-run` o un script de aserción que ya está horneado y cuyo resultado se
loguea a consola con un marcador (`[confine] ...`) que el harness grepea. (Detalle en el plan.)

## 6. Componentes / archivos

| Archivo | Responsabilidad |
|---|---|
| `phase3/apparmor/astromeshd` (new) | Perfil AppArmor nombrado, deny-by-default, para el daemon. |
| `phase3/apparmor/20-apparmor.conf` (new) | Drop-in systemd: `AppArmorProfile=astromeshd`. |
| `phase3/apparmor/confine-check.sh` (new) | Self-check in-guest: confinado + sin-denials + bloqueo positivo → marcador de consola. |
| `phase3/apparmor/confine-check.service` (new) | Oneshot que corre el self-check tarde en boot. |
| `mkosi.conf` (mod) | Packages apparmor/apparmor-utils; cmdline LSM si hace falta. |
| `mkosi.postinst.chroot` (mod) | Instalar perfil + drop-in + self-check; enable apparmor; caché→/var. |
| `tests/boot/confine-and-assert.sh` (new) | Gate: funcional (health+query) + grep del marcador del self-check. |
| `tests/local/dev-loop.sh` (mod) | Target `confine`. |
| `.github/workflows/phase3-confine.yml` (new) | Job `confine-gate`. |

> Nota de diseño: las aserciones (2)-(4) las hace un self-check **dentro del guest**
> (`confine-check.{sh,service}`) que loguea `[confine] CONFINED OK` / `NO-DENIALS OK` /
> `POSITIVE-BLOCK OK` a consola; el harness del host solo verifica health+query y grepea esos
> marcadores. Esto mantiene la lógica AppArmor donde corren `aa-exec`/journal.

## 7. Criterios de done

- Local `dev-loop.sh confine` → `CONFINE GATE PASSED` (funcional + confinado enforce + sin denials
  + bloqueo positivo).
- CI `phase3-confine.yml` verde incluyendo `confine-gate`.
- Gates de Fase 0/2/3.1 siguen verdes (confinamiento no rompió health/update/rollback/no-shell).
- Spec roadmap de Fase 3 actualizado; 3.2 marcado done con referencia de run.

## 8. Riesgos

| Riesgo | Mitigación |
|---|---|
| Transición AppArmor + python del venv finicky | Named-profile via `AppArmorProfile=` (no path-attach); refinar exec/ix en complain |
| `/etc` read-only rompe la caché del parser | Redirigir caché a `/var`; o aceptar recompilación en boot (sin caché) |
| Kernel cloud no activa AppArmor por default | Verificar `aa-enabled`; agregar `apparmor=1 security=apparmor` al cmdline si hace falta |
| Hunt complain→enforce iterativo (varios ciclos) | Igual que 3.1: dev-loop local rápido; el plan incluye el loop explícito |
| El bloqueo positivo elegido falla por DAC, no por AppArmor | Elegir una acción denegada SOLO por el perfil (ruta world-accesible pero fuera de la allow-list), aislada del control DAC |
