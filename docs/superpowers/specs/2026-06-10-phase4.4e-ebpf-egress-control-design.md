# Fase 4.4e — Control real: enforcement de egress por quota (eBPF deny + Rust) — Diseño

> **Estado:** Diseño aprobado en brainstorm (2026-06-10).
> **Tipo:** Cierre del diferencial §12.6→§12.4 — el daemon Rust pasa de medir a **decidir y hacer
> enforcement**: una quota de egress por destino que el eBPF dropea. Construye sobre 4.4d (Rust control).
> **Precede:** 4.4d (daemon Rust load/attach/read/export).
> **Alcance elegido (brainstorm):** **quota dinámica por destino (deny)** — decisión del daemon basada
> en lo observado. Rate-limit fino y políticas más ricas → futuro.

---

## 0. Contexto y propiedad objetivo

El núcleo defendible de §12 es **confianza + atribución + densidad**: 12.1 (sandbox), 12.4 (gobierno de
egress), 12.6 (atribución causal). 4.4 midió el egress por-flujo (eBPF); 4.4d puso el control en Rust. Lo
que faltaba es **enforcement causal**: el daemon decide, basado en lo que observó, y el kernel lo
ejecuta. Esta fase entrega exactamente eso — una **quota de egress por destino**: cuando un agente
excede su presupuesto de bytes hacia un destino, el daemon Rust escribe ese destino a un `deny` map y el
programa eBPF dropea el egress siguiente. Es "atribución → enforcement" en una pieza.

### 0.1 Realidad (discovery)

- **El eBPF actual** (`egress_acct.bpf.c`) es `cgroup_skb/egress`, cuenta por-flujo en `flows` y retorna
  `1` (allow). Agregar un `deny` map y un check al inicio (`return 0` si denegado) lo vuelve enforcement.
- **`cgroup_skb/egress` return 0 dropea el skb**, incluido loopback — confirmar en el gate que corta
  efectivamente el request del runtime al stub (`127.0.0.1:8081`).
- **El daemon Rust** (4.4d) ya lee `flows` y exporta; agregar la lógica de quota (escribir `deny`) es
  incremental, misma pieza.
- **Quota configurable** vía machine-config (`ebpf_egress_quota` → `spec.ebpf.egress.quota_bytes`);
  default ALTO fuera del gate (no deniega nada sin config explícita). El gate la pone baja (500).
- **OS-only:** sin cambio de runtime (sin rebuild del `.deb`, sin `runtime.pin`).

## 1. Arquitectura y flujo de datos

```
egress_acct.bpf.c (extendido):  deny  BPF_MAP_TYPE_HASH {flow_key}->u8
  cgroup_skb/egress:
    if bpf_map_lookup(deny, flow_key) -> return 0   (DROP, no cuenta)
    else  -> count en flows -> return 1             (allow, como 4.4)
       ▲ deny.update(key,1)                          │ lee flows
astromesh-ebpf (Rust, 4.4d + control):               ▼
  quota = spec.ebpf.egress.quota_bytes (runtime.yaml)
  loop 10s: por cada flujo con bytes > quota -> deny.update(key,1) + log "[ctl] DENY <daddr:dport>"
            (sigue exportando OTLP como 4.4d)
```

El daemon decide (quota excedida) y el eBPF ejecuta (drop). Demostrable: un agente que supera su quota
hacia el provider ve sus llamadas cortadas a nivel kernel.

## 3. El gate (`tests/boot/ebpf-control-and-assert.sh`)

1. Boot 1 VM con machine-config `ebpf_egress: true` + `otel: true` + `ebpf_egress_quota: 500`.
2. Assert consola `ASTROMESH-EBPF ATTACHED OK`. Espera `/v1/health`.
3. POST corridas repetidas al `phase0-smoke` (stub) → el flujo a `127.0.0.1:8081` supera los 500 bytes.
4. Assert **decisión**: el daemon logueó `[ctl] DENY 127.0.0.1:8081`.
5. Assert **enforcement**: una corrida POSTerior al deny no logra hablar con el provider — el egress a
   8081 se dropea. Forma concreta (discovery): la respuesta del `/v1/agents/.../run` indica error de
   provider (5xx / `answer` vacío / timeout), o el flujo deja de crecer. Marker `[ctl] EGRESS-DENY ENFORCED OK`.
6. `[otel] EBPF CONTROL GATE PASSED`.

**Discovery+iterate:** (a) que el drop de loopback corte el request; (b) cómo se manifiesta el fallo en
la respuesta del agente — se confirma en el primer gate y se ajusta la assertion (como los gates empíricos
de 4.2/4.4).

## 4. Criterios de done

- Local `dev-loop.sh ebpf-control` → `EBPF CONTROL GATE PASSED` (el daemon deniega + el eBPF dropea).
- CI `phase4-ebpf-control.yml` verde.
- Gates previos verdes: `ebpf-rust` (sin quota baja, no deniega nada — quota default alta), `otel`,
  `egress`, `machineconfig`. La guarda (doble flag) no-opea el daemon fuera del boot combinado.
- Roadmap: el control real marcado done.

---

## 5. Riesgos

| Riesgo | Mitigación |
|---|---|
| El drop de loopback no corta el request del runtime | `cgroup_skb/egress` return 0 dropea el skb; confirmar en el gate (discovery). Si no, denegar un dst no-loopback. |
| Romper `ebpf-rust` (4.4d) con la quota | Default ALTO (no deniega sin config); `ebpf-rust` no setea quota → no deniega → idéntico a 4.4d. |
| El daemon deniega flujos legítimos en prod | Quota off por default (alta); sólo deniega con `ebpf_egress_quota` explícito. Documentado. |
| Verificar el enforcement en el gate (no solo la decisión) | Assertar AMBOS: el marker `DENY` (decisión) y un efecto observable (corrida fallida / flujo plateau). Discovery ajusta la forma. |
| El daemon se auto-ciega denegando su propio pipe OTLP (`127.0.0.1:4317`) | **Descubierto en el primer gate** (la quota baja denegó el colector): el loop **exime** el endpoint OTLP del enforcement (`is_own_telemetry`). La observabilidad nunca se corta a sí misma. |

---

## 6. Fuera de alcance (futuro)

- **Rate-limit fino** (token bucket en eBPF, por-flujo, con timestamps).
- **Per-agente enforcement** (cuota por agent-run — necesita el join socket→agente de 4.4c-kernel).
- **Políticas ricas** (allow/deny por CIDR, por hora, feedback al runtime para reintentos).
- **Undeny / TTL** del deny map (re-permitir tras una ventana).
