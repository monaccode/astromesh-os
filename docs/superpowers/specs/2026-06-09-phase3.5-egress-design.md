# Fase 3.5 — Gobierno de egress del runtime (deny-by-default IP/CIDR vía systemd) — Diseño

> **Estado:** Diseño aprobado en brainstorm (2026-06-09).
> **Tipo:** Spec de sub-proyecto (Fase 3, sub-proyecto **F** fail-closed §12.4). Alimenta un plan (writing-plans).
> **Precede:** Fase 3.1 (no-shell+break-glass), 3.2 (AppArmor), 3.3 (TPM-sealed secret), 3.4 (sandbox
> seccomp/ns), 3.6 (Secure Boot) cerradas. Construye sobre la misma imagen y patrones de gate.

---

## 0. Contexto y propiedad objetivo

Gate de Fase 3 (decomposición §6.7 / §12.4, ADR-4): **gobierno del egress de red del runtime**,
fail-closed ("el OS debe garantizar … gobierno de egress (12.4) o no arrancar el agente"). Es la
segunda mitad del núcleo defendible del diferencial **F** (la primera, aislamiento 12.1, la cubrió
3.4 a nivel syscalls/namespaces).

**Realidad del runtime (clave para el alcance):** `astromeshd` es `/opt/astromesh/venv/bin/python3`
corriendo el agente. Hoy su red está **abierta**: AppArmor 3.2 permite `network inet stream` /
`network inet6 stream` (TCP a cualquier destino) y el sandbox 3.4 restringe *familias* de direcciones
(`RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX`) pero **no destinos**. Un agente comprometido o
una tool in-process puede abrir TCP a cualquier IP (exfiltración / C2). No existe gobierno de egress.

**Decisión de alcance (brainstorm):** aplicar **deny-by-default de egress** a `astromeshd` vía las
directivas `IPAddressDeny=`/`IPAddressAllow=` de systemd. Bajo el capó systemd **compila e instala
programas BPF de cgroup/skb** que filtran el tráfico del cgroup del servicio: es **egress eBPF real**,
fail-closed, construible y gateable en el harness QEMU/WSL2/CI actual, **sin escribir Rust+eBPF**.

**Por qué esto y no XDP/tc-bpf custom:** el XDP/tc-bpf propio en Rust (aya/libbpf-rs) es el §12.4
"full" y máximo diferencial, pero activa de lleno la dependencia de talento más crítica del proyecto
(Rust+eBPF, R3/ADR-10) y probablemente exige nested-virt en CI. Se **difiere a Fase 4**, con el mismo
criterio con que 3.4 difirió el microVM por-tool. El MVP entrega la *propiedad* (egress gobernado,
fail-closed) con mecanismo eBPF-backed de systemd.

**Por qué complementa y no reemplaza capas previas:** AppArmor restringe *qué rutas/recursos* toca el
proceso; seccomp *qué syscalls*; namespaces/privilegios *qué puede crear/escalar*; **egress IP
deny-by-default *con quién puede hablar por red***. Defensa en profundidad: un bug que evada una capa
choca con la otra.

## 1. Objetivo y alcance

**Objetivo:** que `astromeshd` corra con egress **deny-by-default** (sólo destinos en un allowlist
IP/CIDR) aplicado por systemd, y que **no arranque** si ese gobierno no puede activarse (fail-closed).

**En alcance (3.5):**
- Drop-in de egress en `astromeshd.service` (`IPAddressDeny=any` + `IPAddressAllow=<allowlist>`).
- Self-check fail-closed (oneshot `Before=astromeshd`, **bajo el mismo filtro IP**) que verifica que
  el gobierno está activo y prueba **POSITIVE-ALLOW** (un destino permitido es alcanzable) y
  **POSITIVE-BLOCK** (un destino no permitido es efectivamente rechazado).
- Wiring fail-closed: `astromeshd` `Requires=` el self-check (no arranca si el egress no quedó gobernado).
- Gate de boot (KVM local + CI) que prueba marcadores + `astromeshd` healthy bajo el gobierno de egress.

**Fuera de alcance (explícito):**
- XDP/tc-bpf custom en Rust (§12.4 full) → Fase 4, gated por talento Rust+eBPF (R3/ADR-10).
- Atribución causal de egress por-flujo (§12.6) → Fase 4.
- Proxy de egress con allowlist **por-hostname** (granularidad por-dominio) → fast-follow documentado.
  El MVP es IP/CIDR; el filtrado por SNI/CONNECT agrega un componente nuevo y su confinamiento (YAGNI).
- Generator systemd que materialice el allowlist desde `/etc/astromesh/egress-allow.conf` → fast-follow.
- Egress UDP arbitrario: el allowlist cubre DNS (UDP/53 al resolver) y TCP a destinos permitidos; no
  se abre egress UDP general.

**Invariante:** no romper gates de Fase 0/1/2/3.1/3.2/3.3/3.4/3.6 (health, A/B update, rollback,
no-shell, confinamiento, TPM-unseal, sandbox, Secure Boot). El gobierno de egress es **aditivo**.
Como `/v1/health` es **loopback** (`127.0.0.1:8000`) y loopback está en el allowlist, los gates de
salud siguen verdes. El plan re-corre rollback (Fase 2), confine (3.2), tpm (3.3) y sandbox (3.4)
como regresión.

## 2. El drop-in de egress (`phase3/egress/40-egress.conf`)

`astromeshd.service.d/40-egress.conf`. Directivas y razón:

| Directiva | Efecto |
|---|---|
| `IPAddressDeny=any` | **Deny-by-default**: deniega todo egress/ingress IP del cgroup del servicio salvo lo explícitamente permitido. systemd instala el programa BPF de filtrado en el cgroup. |
| `IPAddressAllow=localhost` | Permite loopback (IPv4 `127.0.0.0/8` + IPv6 `::1/128`): habilita `/v1/health` y cualquier IPC local. |
| `IPAddressAllow=<DNS resolver CIDR>` | Permite alcanzar el/los resolver(s) DNS (p.ej. la IP de `nameserver` en `/etc/resolv.conf`). Sin esto, la resolución de nombres del provider rompe. |
| `IPAddressAllow=<provider CIDRs>` | **Deployment-specific**: los CIDRs del provider frontier (Anthropic). Default embarcado **vacío** (ver §4); producción los agrega. |

Notas:
- `IPAddressAllow=`/`Deny=` son **aditivos por el árbol de slices**: el filtro efectivo del servicio
  es la unión con el de sus slices padre. Se ancla el servicio para que su filtro no quede aflojado
  por un `IPAddressAllow=any` heredado: el drop-in declara `Slice=astromesh.slice` (slice dedicada)
  o, mínimamente, no se confía en defaults heredados (el plan verifica el filtro efectivo con
  `systemctl show -p IPAddressAllow,IPAddressDeny`).
- Es **aditivo** al `AppArmorProfile=astromeshd` (3.2), al sandbox `30-sandbox.conf` (3.4) y al
  `EnvironmentFile=-/run/astromesh/env` (3.3). `IPAddressAllow=localhost` no afecta el unseal (que
  escribe `/run`, no red).
- AppArmor 3.2 sigue permitiendo `network inet stream` (capa de *familia/protocolo*); el egress IP de
  systemd es la capa de *destino*. Ortogonales; no se toca el perfil AppArmor.

**Wiring fail-closed (en el mismo drop-in o uno adyacente):**
`Requires=astromesh-egress-check.service` + `After=astromesh-egress-check.service` en
`astromeshd.service` → si el check falla, `astromeshd` **no arranca**.

## 3. El self-check fail-closed (`phase3/egress/astromesh-egress-check.{sh,service}`)

Oneshot, `Before=astromeshd.service`, que corre **bajo el mismo filtro de egress** (lleva el mismo
`IPAddressDeny=any` + `IPAddressAllow=` que el drop-in, para probar la política real como proxy del
servicio de astromeshd, que aún no arrancó).

El script (`set -euo pipefail`):
1. **POLICY-ACTIVE OK** — confirma que el gobierno está aplicado: `IPAddressDeny=any` efectivo en el
   propio cgroup (vía `systemctl show astromeshd -p IPAddressDeny,IPAddressAllow` mostrando deny no
   vacío, y/o presencia del filtro BPF). Si no hay deny efectivo → FAILED (fail-closed: si systemd no
   instaló el filtro, no seguimos).
2. **POSITIVE-ALLOW OK** — un destino **permitido** es alcanzable: connect TCP a `127.0.0.1:8000`
   (loopback, en el allowlist real de prod). Prueba que la mitad "allow" funciona — que el filtro no
   es fail-open contra el propio runtime.
3. **POSITIVE-BLOCK OK** — un destino **no permitido** es rechazado: connect TCP al gateway de
   QEMU user-net `10.0.2.2:<port>` (no está en el allowlist; alcanzable absent-filter, así que el
   bloqueo es significativo) → debe fallar con `EPERM`/`EACCES` (errno de filtro BPF) o timeout corto.
   Confirma que el deny-by-default es efectivo. (Análogo al POSITIVE-BLOCK de 3.2/3.4.)
4. Emite `[egress] EGRESS GATE OK` si todo pasa; cualquier fallo → `[egress] … FAILED` + exit≠0, lo
   que (por `Requires=`) impide el arranque de `astromeshd` y deja el gate en rojo.

Marcadores a consola (`StandardOutput=journal+console`): `[egress] POLICY-ACTIVE OK`,
`[egress] POSITIVE-ALLOW OK`, `[egress] POSITIVE-BLOCK OK`, `[egress] EGRESS GATE OK`.

> Nota sobre el destino de BLOCK: `10.0.2.2` es el gateway de QEMU user-net, presente en todo boot del
> harness y **fuera** del allowlist de prod (loopback+DNS). Es la elección refinada en brainstorm:
> probar el bloqueo contra la **política real** sin contaminar el allowlist de prod con IPs de test.
> El connect debe usar un timeout corto (p.ej. `timeout 3 bash -c '…/dev/tcp/10.0.2.2/9'`) para que
> un drop silencioso no cuelgue el oneshot.

## 4. Provisioning del allowlist (default seguro + extensión de producción)

- **Default embarcado:** `IPAddressAllow=localhost` + el/los CIDR(s) del resolver DNS. **Sin** CIDRs
  de provider por default. Justificación: Anthropic no publica CIDRs estables/oficiales, y un default
  amplio sería deny-by-default en nombre solamente. Con loopback permitido, **todos los gates de salud
  siguen verdes** (health es loopback).
- **Extensión de producción:** el operador agrega los CIDRs del provider editando el drop-in
  (documentado en `phase3/egress/README.md`, mismo patrón que las TEST keys de 3.6). Hasta que se
  agreguen, el agente puede servir health pero **no** alcanza el provider — *fail-closed por diseño*:
  preferible a egress abierto.
- **Fast-follow (fuera del MVP):** un generator systemd que lea `/etc/astromesh/egress-allow.conf`
  (una IP/CIDR por línea) y materialice el drop-in, para gestionar el allowlist como config sin editar
  units. Documentado, no implementado en 3.5.

## 5. El gate (`tests/boot/egress-and-assert.sh`)

Un solo boot (patrón de 3.1/3.2/3.4, KVM local / TCG CI):
1. Boot normal; el self-check emite marcadores bajo el filtro de egress real.
2. El harness grepea `[egress] EGRESS GATE OK` en la consola (incluye POLICY-ACTIVE / POSITIVE-ALLOW /
   POSITIVE-BLOCK) y verifica `astromeshd` `/v1/health` 200 (prueba que el gobierno de egress **no
   rompió** el runtime — la mitad allow no es fail-open contra el propio agente, y el deny no mató la
   salud loopback).
3. Veredicto: `[egress] EGRESS GATE PASSED`.

El gate es **auto-contenido**: no requiere internet ni token de provider. POSITIVE-ALLOW usa loopback;
POSITIVE-BLOCK usa el gateway de QEMU. Determinista bajo KVM y TCG.

## 7. Criterios de done

- Local `dev-loop.sh egress` → `EGRESS GATE PASSED` (marcadores POLICY-ACTIVE/POSITIVE-ALLOW/
  POSITIVE-BLOCK + `astromeshd` healthy bajo el gobierno de egress).
- CI `phase3-egress.yml` verde incluyendo `egress-gate`.
- Gates de Fase 0/2/3.1/3.2/3.3/3.4/3.6 siguen verdes (el drop-in es aditivo; no rompió health/update/
  rollback/no-shell/confine/unseal/sandbox/Secure Boot).
- Fail-closed demostrado: si el filtro de egress no puede aplicarse, `astromeshd` no arranca (vía
  `Requires=egress-check` + el POSITIVE-BLOCK).
- Spec roadmap de Fase 3 actualizado; 3.5 marcado done con referencia de run.

## 8. Riesgos

| Riesgo | Mitigación |
|---|---|
| `IPAddressDeny=any` rompe la resolución DNS (egress al resolver) | El allowlist incluye el CIDR del resolver DNS; el gate valida health (que en el agente real implica DNS+provider). Self-check POSITIVE-ALLOW lo cubre por loopback; el plan añade un check DNS si el runtime lo requiere para health. |
| El kernel/initrd no soporta el BPF de `IPAddress*` (CONFIG_CGROUP_BPF) | Debian trixie / kernel 6.12 (ADR-3) trae cgroup-BPF. El POLICY-ACTIVE check falla fail-closed si systemd no pudo instalar el filtro, así que un kernel sin soporte se detecta (no pasa silenciosamente). |
| Filtro efectivo aflojado por `IPAddressAllow=` heredado de una slice padre | Anclar a `astromesh.slice` dedicada y verificar el filtro efectivo con `systemctl show -p IPAddressAllow,IPAddressDeny`; el POSITIVE-BLOCK confirma empíricamente que el deny es efectivo. |
| POSITIVE-BLOCK cuelga el oneshot si el destino dropea en silencio | Connect con `timeout` corto; tratar timeout **como** bloqueo exitoso (deny BPF puede dropear sin RST). |
| `Requires=egress-check` tiene blast-radius (un bug del check tumba astromeshd y todos los gates) | Check simple/robusto; `set -euo pipefail`; probar primero en el gate de 3.5 antes de confiar en la regresión. |
| Default sin provider CIDRs deja al agente sin alcanzar el provider | **Intencional** (fail-closed). Documentado en README; producción agrega CIDRs. Health (loopback) no se ve afectado, así que los gates siguen verdes. |
| Interacción con egress real al provider en una query de agente (Fase 0) | La validación de query real de Fase 0 es manual/one-off (CI no tiene token); el MVP no la automatiza. Con provider CIDRs agregados, el egress al provider funciona; sin ellos, falla cerrado (esperado). |
