# Fase 4.4c — Atribución de egress por-agente (app-side) vía OTel — Diseño

> **Estado:** Diseño aprobado en brainstorm (2026-06-10).
> **Tipo:** Refinamiento de Fase 4 (per-agente del §12.6, **app-side**) — vertical de runtime, reusa el
> pipeline OTLP de 4.3 + el pipeline de métricas de 4.4b.
> **Precede:** 4.3 (collector + export OTLP del nodo) + 4.4b (pipeline `metrics` en el collector).
> **Alcance elegido (brainstorm):** **app-side** (el runtime mide bytes de egress por-agente y los
> exporta vía OTel). El join **kernel-causal** queda descartado para per-agente (lo rompe el pooling de
> conexiones). El **control Rust** es una fase aparte (4.4d).

---

## 0. Contexto y propiedad objetivo

§12.6 quiere atribución causal de costo **por agente**. 4.4 dio la vista kernel por-flujo (cgroup);
4.4b la exportó por OTel. El per-agente kernel-causal está **comprometido**: `openai_compat` reusa un
`httpx.AsyncClient` (keep-alive), así que **una conexión TCP sirve a muchos agent-runs** → atribuir por
socket-cookie es incorrecto; y SO_MARK está bloqueado (astromeshd non-root). La atribución **precisa**
por-agente vive donde está el contexto: el **runtime** (el engine sabe qué agente hace cada llamada al
provider). 4.4c la mide ahí y la exporta vía el mismo OTLP de 4.3.

### 0.1 Realidad (discovery)

- **"Egress" = bytes salientes** (el request al provider), consistente con el eBPF de 4.4. El response
  es ingress (no se cuenta acá).
- **El engine conoce el agente** (`self.name`) y los mensajes en `model_fn`, justo donde llama a
  `router.route(...)`. Ahí se mide `request_bytes` sin threadear nada al provider.
- **El venv ya tiene el SDK de métricas** (verificado en 4.4b: `MeterProvider` + `OTLPMetricExporter`).
  → el runtime arma su propio `MetricsManager`, igual que `TelemetryManager` para trazas (4.3).
- **El collector ya recibe métricas** (pipeline `metrics` de 4.4b). El export del nodo va a
  `127.0.0.1:4317` (el mismo endpoint que las trazas, del config).
- **Endpoint:** reusa `observability.otlp.endpoint` (default `http://127.0.0.1:4317`) y el flag
  `observability.otlp.enabled` (4.3). Guarda igual que las trazas.

## 1. Arquitectura y flujo de datos

```
engine.run() model_fn (nodo) — agente=self.name, model, full_messages
   │ request_bytes = len(serialize(full_messages))
   ▼ MetricsManager.record(agent, model, request_bytes)
node MetricsManager: Counter astromesh.agent.egress.bytes{agent,model} (cumulative)
   │ MeterProvider + OTLPMetricExporter(endpoint) ; force_flush (como las trazas de 4.3)
   ▼ OTLP/gRPC → 127.0.0.1:4317
otelcol sidecar (4.3 + pipeline metrics de 4.4b) → debug → consola
   ▼
gate: asserta astromesh.agent.egress.bytes{agent=phase0-smoke} en el dump del collector
```

Un solo VM. Sin eBPF, sin helper privilegiado, sin SO_MARK — atribución exacta por-agente en la capa
de app, evitando el pooling. Reusa el collector y los flags de 4.3/4.4b.

## 3. El gate (`tests/boot/agent-egress-otlp-and-assert.sh`)

1. Boot 1 VM con machine-config `otel: true` (sin ebpf — app-side puro).
2. Assert consola `[otel] OTEL-COLLECTOR OK`; espera `/v1/health`.
3. POST corridas al `phase0-smoke` (stub) → el engine emite `astromesh.agent.egress.bytes{agent=phase0-smoke}`.
4. Assert consola: el collector dumpeó la métrica `astromesh.agent.egress.bytes` con `agent: Str(phase0-smoke)`
   y `Value > 0`. Marker `[otel] AGENT-EGRESS-EXPORTED OK`.
5. `[otel] AGENT EGRESS GATE PASSED`.

**Discovery+iterate:** el formato del debug-exporter para el atributo string (`agent: Str(phase0-smoke)`)
y el `Value` se confirman en un host-test (como 4.4b) antes del gate; se ajusta el grep.

## 5. Riesgos

| Riesgo | Mitigación |
|---|---|
| Pooling rompe el per-agente kernel | Por eso es **app-side**: el engine atribuye exacto por agente, sin depender del socket. |
| `request_bytes` aproximado (no incluye headers/TLS) | Es una métrica de atribución de payload, no de wire exacto; documentado. Suficiente para "agente X envió ~N bytes". |
| Doble setup OTel (trazas + métricas) en el nodo | `MetricsManager` separado del `TelemetryManager`; ambos al mismo endpoint; reusan el guard. |
| Salto de runtime al rebuildear el `.deb` | Mismo proceso que 4.3: rebuild + bump `runtime.pin` + re-correr regresiones contra el runtime nuevo. |
| Cambiar comportamiento de gates previos | Guarda por `observability.otlp.enabled` (off por default); fuera de boots otel es no-op. |

- Métricas adicionales por-agente (CPU, tokens ya en spans, etc.).
