# Fase 4.3 — OTel exportando (spans a un collector) — Diseño

> **Estado:** Diseño aprobado en brainstorm (2026-06-10).
> **Tipo:** Spec de sub-proyecto (Fase 4 — Observabilidad §6.8, capa de export OTel; la atribución
> causal eBPF §12.6 es 4.4 y cierra el círculo).
> **Precede:** Fase 4.1 (machine-config) + 4.2 (malla). Reusa el patrón "unidad guardada por perfil"
> de 4.2 y el render de `runtime.yaml` de 4.1.
> **Alcance elegido (brainstorm):** vertical completo (nodo + OS), **solo traces** (métricas → 4.3b),
> collector **sidecar horneado** en la imagen.

---

## 0. Contexto y propiedad objetivo

Gate de Fase 4 (§6.8 observabilidad): el nodo **exporta su telemetría (spans) a un collector OTel**.
4.1 entregó la config declarativa; 4.2 la malla; 4.3 entrega la **telemetría exportada**: los spans que
el runtime ya genera por cada agent-run salen del nodo vía OTLP a un OpenTelemetry Collector.

### 0.1 Realidad del runtime (clave para el alcance — discovery)

El runtime (`../astromesh`, empaquetado como `astromesh-node` `.deb` v0.1.1, pineado) **ya trae** toda
la instrumentación de traces, pero el export OTLP está **dormido**:

- **Instrumentación interna activa:** `engine.run()` construye un `TracingContext` con un árbol de spans
  por cada corrida de agente — `agent.run`, `memory_build`, `prompt_render`, `llm.complete`,
  `tool.call` — con atributos ricos (modelo, tokens, costo, latencia). (`astromesh/runtime/engine.py`.)
- **Puente OTLP presente pero sin instanciar:** `astromesh/observability/telemetry.py`
  (`TelemetryManager` + `TelemetryConfig`, default `otlp_endpoint="http://localhost:4317"`) y
  `observability/collector.py` (`OTLPCollector(InternalCollector)`, "Bridges TracingContext spans to
  OpenTelemetry") existen, y las deps `opentelemetry-api/sdk/exporter-otlp>=1.27` están declaradas en
  `astromesh-node/pyproject.toml` → **van en el venv del `.deb`**. Pero `TelemetryManager(` solo se
  construye en tests, `.setup()` nunca se llama, y `traces.py` usa `_collector = InternalCollector()`
  (in-memory, `/v1/traces`), no `OTLPCollector`.
- **Gap adicional:** `emit_trace()` **no tiene llamador** en el runtime — el engine arma el
  `TracingContext` pero nada lo entrega al collector. Activar el export requiere también **cablear el
  emit** al final de `engine.run()`.
- **Métricas:** `/v1/metrics` devuelve JSON in-memory (`{counters, histograms}`), sin path OTel/Prom
  exportado. **Fuera de alcance de 4.3** (→ 4.3b: OTel MeterProvider + reader periódico).

Conclusión: "OTel exportando" requiere **activar** el puente (cambio de fuente en el nodo) **y** la
infraestructura de OS (collector sidecar + config + gate). Por eso el alcance es vertical (dos repos).

## 1. Arquitectura y flujo de datos

Un solo VM. El nodo exporta a un collector **local** en `localhost:4317` (el default del SDK → cero
config de dirección en el nodo). El collector recibe OTLP/gRPC y, en el gate, vuelca los spans
recibidos a su stdout (`debug` exporter) → journal → consola, que el gate inspecciona.

```
astromeshd (nodo)                          OTel Collector sidecar (horneado)
 engine.run() arma TracingContext           ┌──────────────────────────────┐
   spans: agent.run, memory_build,          │ receivers:  otlp (grpc :4317)│
   prompt_render, llm.complete, tool.call    │      ↓                        │
        │ emit_trace(ctx)   (cableado 4.3)   │ processors: batch            │
        ▼                                    │      ↓                        │
 OTLPCollector (puente)  ─ OTLP/gRPC ───────▶│ exporters:  debug   (gate)   │─▶ journal→consola
   → OTel SDK → OTLPSpanExporter             │             otlp    (prod,   │   (el gate asserta)
     endpoint = localhost:4317               │              machine-config) │─▶ backend de flota
                                             └──────────────────────────────┘
```

El segundo exporter `otlp` (downstream a la flota; dirección desde machine-config, **deshabilitado por
default**) es el path productivo — mismo patrón "valor de gate comiteado, prod reemplaza" que la CIDR de
egress (3.5) y la CA de cluster (4.2).

## 2. Cambio de fuente en el nodo (`../astromesh`, quirúrgico)

Activar el puente OTLP existente, **config-driven**, y **off por default** (cero cambio de
comportamiento para nodos/tests existentes):

1. **Startup (`astromesh-node/src/astromesh_node/daemon/core.py`):** cuando el export OTLP está
   habilitado, construir `TelemetryManager(TelemetryConfig(otlp_endpoint=…, enabled=True))`, llamar
   `.setup()`, y `set_collector(OTLPCollector(telemetry_manager=tm))` (reemplaza el `InternalCollector`
   default).
2. **Cablear el emit:** llamar `await get_collector().emit_trace(tracing)` al final de `engine.run()`
   (hoy el sink no tiene llamador). Un code-explorer confirma el punto exacto y que `/v1/traces`
   comparte el mismo collector (así el internal sigue funcionando además del OTLP).
3. **Fuente de config:** un bloque nuevo `observability.otlp` en el `RuntimeConfig`
   (`enabled: bool`, `endpoint: str = "http://localhost:4317"`), y honrar `OTEL_EXPORTER_OTLP_ENDPOINT`.
   Default `enabled: false`.

**Limitación conocida (aceptable para el MVP, documentada):** `OTLPCollector.emit_trace` re-emite cada
span como un span OTel **nuevo** al momento del emit (`start_as_current_span(name)` + atributos), así
que se **aplanan** los trace/span IDs originales, los enlaces padre y los timestamps. Los spans
**llegan** al collector (satisface el gate); preservar IDs/parentesco/tiempos es refinamiento 4.3b.

sin ese flag) **completamente intactos**.

## 4. El gate (`tests/boot/otel-export-and-assert.sh`)

1. Bootea **1 VM** con un machine-config (SMBIOS, patrón 4.1) sobre un perfil estándar (p.ej. `worker`)
   **más el campo `otel`** en la credencial → `machine-config.sh` fija `observability.otlp.enabled: true`
   (endpoint `localhost:4317`) en el `runtime.yaml` renderizado. (No es un perfil nuevo; el flag lo
   activa la credencial, igual que 4.2 activa la malla por `mesh_ip`/`peer_ip`.) `-nic user,hostfwd`
   para que el host lea `/v1`.
2. Espera `/v1/health` 200. Asserta que la consola muestra `[otel] OTEL-COLLECTOR OK` (el collector
   bindeó `:4317` antes de astromeshd).
3. **Disparar un span:** POST una query al **smoke agent phase0 horneado** vía `/v1` en **modo stub**
   (el dev-loop ya buildea con `PHASE0_MODE=stub`; el provider es un stub local, sin API key real). El
   árbol `agent.run`/`memory_build`/`prompt_render` se emite igual.
4. **Assertar export:** grep en la salida del collector (consola) por el span exportado — `agent.run` y
   `service.name=astromesh`. Imprime `OTEL EXPORT GATE PASSED`.

**Negativo/regresión:** un boot sin el flag (cualquier gate previo) → la unidad otel hace no-op, el
collector no corre, astromeshd no exporta. Confirmado por la convención de guarda.

## 5. Componentes y aislamiento

- **Nodo (puente OTLP):** entrada = `TracingContext` del engine + config `observability.otlp`; salida =
  spans OTLP a `endpoint`. Testeable aislado (test del nodo: con export on y un receptor dummy, los
  spans salen).
- **Collector sidecar:** entrada = OTLP `:4317`; salida = `debug` (consola) + `otlp` (downstream). Es un
  binario estándar; su contrato es la config YAML. Testeable aislado.
- **machine-config (mod):** entrada = credencial SMBIOS; salida = `observability.otlp.*` en
  `runtime.yaml` + arranque guardado de la unidad. Reusa el parse PyYAML de 4.1/4.2.
- **Gate:** orquesta 1 VM + smoke agent + assert. Independiente del backend real (usa `debug`).

## 7. Riesgos

| Riesgo | Mitigación |
|---|---|
| El `.deb` pineado no exporta sin cambio de fuente (puente dormido) | El alcance es vertical: el cambio de nodo en `../astromesh` se rebuildea al `.deb` (el dev-loop ya rebuildea el deb). Discovery confirma el punto de `set_collector` + `emit_trace`. |
| `emit_trace` sin llamador → spans nunca salen | Tarea explícita de cablear el emit al final de `engine.run()`; un code-explorer mapea el path antes de tocar. |
| Tamaño de imagen — el `otelcol` prebuilt (core 123 MB / k8s ~140 MB) NO entra en la raíz fija de 448 MB | Build **mínimo vía ocb** (~26 MB) con sólo los componentes usados. Horneado SÓLO en builds otel (condicional a `dist/otelcol`), así los demás gates no cargan el binario ni pagan tamaño. |
| El postinst de mkosi no tiene red (no se puede bajar el binario ahí) | Construir el collector en el HOST/CI (ocb, necesita Go) y entregarlo como build-input `dist/otelcol`; el postinst sólo lo instala si está presente — mismo modelo que el `.deb`. |
| `opentelemetry` no va en el venv del `.deb` (está en el extra `observability` del core) | `build-deb.sh` instala `../[observability]`; si no, `TelemetryManager.setup()` da ImportError y el export hace no-op silencioso. |
| **`libstdc++6` falta en la imagen** → la C-ext de grpcio (cygrpc) no importa → `setup()` cae a `tracer=None` y el export hace no-op silencioso (EL bloqueador real) | Hornear `libstdc++6` en `mkosi.conf`. `setup()` ahora **avisa** en vez de no-opear en silencio. |
| El BatchSpanProcessor no exporta por timer bajo el sandbox del nodo (+ canal gRPC frío) | El puente hace `provider.force_flush()` tras emitir; entrega determinista. |
| `localhost` → `::1` (IPv6) pero el collector escucha IPv4-only en `127.0.0.1` | Fijar el endpoint del nodo a `http://127.0.0.1:4317` en el machine-config. |
| Fidelidad de spans (IDs/tiempos aplanados por el puente) | Documentado como limitación MVP; el gate solo exige llegada. Preservar trace context → 4.3b. |
| El stub no emite spans (sin provider real) | `agent.run`/`memory_build`/`prompt_render` se emiten antes del LLM-call; el stub responde local. Confirmar en el gate. |
| Cambiar comportamiento de gates previos | Guarda por `observability.otlp.enabled` (off por default), idéntica a la guarda `mesh.enabled` de 4.2. |

  vía machine-config.
