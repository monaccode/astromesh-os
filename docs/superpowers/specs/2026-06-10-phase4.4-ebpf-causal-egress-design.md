# Fase 4.4 — Atribución causal de egress por-flujo (eBPF) — Diseño

> **Estado:** Diseño aprobado en brainstorm (2026-06-10).
> **Tipo:** Spec de sub-proyecto (Fase 4 — diferencial de kernel **F**, §12.6 atribución causal; arranca
> la rebanada de red, cerrando lo que 3.5 difirió). Es el primer pedazo de eBPF propio del proyecto.
> **Precede:** 3.5 (egress governance, mismo plano cgroup) + 4.3 (OTel — destino futuro de la métrica).
> **Alcance elegido (brainstorm):** **egress por-flujo**, **C-eBPF + bpftool** (sin userspace propio),
> atribución **al cgroup del runtime** (no per-agent-run todavía). Control Rust + join por-agente +
> export OTel → **4.4b**.

---

## 0. Contexto y propiedad objetivo

§12.6 (atribución causal) es el núcleo del diferencial: el OS se justifica por **confianza, atribución
y densidad** (ADR/decomposición §3), no por velocidad. 3.5 entregó **gobierno** de egress
(deny-by-default vía `IPAddressDeny` de systemd) y **difirió** explícitamente la *atribución causal de
egress por-flujo* a Fase 4 (spec 3.5 §"futuro"). 4.4 entrega esa atribución: un programa eBPF propio
contabiliza, **a nivel kernel**, los bytes de egress **por flujo (destino)** que salen del cgroup del
runtime — algo que la capa de app (los spans de 4.3) no ve causalmente.

### 0.1 Realidad del entorno (clave para el alcance — discovery)

- **Kernel:** la imagen trae `6.12.90+deb13.1-cloud-amd64` (ADR-3 lo eligió por eBPF/XDP modernos).
- **Programa eBPF "clásico":** un `cgroup_skb/egress` accede a `struct __sk_buff` (no al skb del kernel)
  y parsea headers IP/TCP/UDP de los uapi headers (`linux/ip.h`, etc.) → **no necesita
  vmlinux.h/BTF/CO-RE en compile-time**. El build es `clang -O2 -target bpf -c`. Portable.
- **Greenfield:** no hay eBPF ni Rust en el repo. 4.4 introduce **clang** (compilar el `.bpf.o` en
  host/CI, igual que el binario de otelcol) y **bpftool** (en la imagen, para cargar/atar/leer).
- **El postinst de mkosi no tiene red ni clang** → el `.bpf.o` se compila en host/CI y se entrega como
  **build-input** `dist/egress_acct.bpf.o` (mismo modelo que el `.deb` y el binario de otelcol en 4.3).
- **Multiplexación cgroup (3.5):** systemd ya ata un `cgroup_skb` (el filtro `IPAddressDeny`) al cgroup
  de astromeshd. Atamos nuestro programa de contabilidad con `BPF_F_ALLOW_MULTI` para que ambos corran.
  Esto es **discovery+iterate** (como el strongSwan de 4.2): el primer gate verifica la coexistencia.

## 1. Arquitectura y flujo de datos

Un solo VM. El programa eBPF contabiliza cada skb de egress del cgroup del runtime, agregando bytes y
paquetes por flujo (destino) en un mapa hash pineado. `bpftool` lo carga/ata/lee; un script vuelca el
mapa. El gate dispara una corrida de agente (llamada al stub) y asserta el flujo contabilizado.

```
cgroup de astromeshd (system.slice/astromeshd.service)
   │ agent run → provider call (stub @127.0.0.1:8081) → skb de egress
   ▼
cgroup_skb/egress  (egress_acct.bpf.o, horneado)
   │ parsea daddr+dport+proto de __sk_buff; acumula bytes+pkts
   ▼
mapa hash "flows"  key={daddr,dport,proto} val={bytes,packets}  (pin /sys/fs/bpf/astromesh/flows)
   │ bpftool map dump
   ▼
egress-acct-dump.sh → marker en consola / archivo   (el gate asserta; export OTel → 4.4b)
```

`cgroup_skb/egress` dispara a nivel socket, así que **ve el tráfico loopback** (la llamada al stub en
`127.0.0.1:8081`) — por eso el gate es demostrable sin red externa, y `127.0.0.1` ya está permitido por
el filtro de egress de 3.5.

## 2. El programa eBPF (`phase4/ebpf/egress_acct.bpf.c`)

- Tipo: `SEC("cgroup_skb/egress")`, retorna `1` (allow — **no filtra**, solo contabiliza; el filtrado
  sigue siendo de 3.5).
- Parsea: `__sk_buff` → `struct iphdr` (IPv4; bounds-check contra `data_end`) → `daddr`; si TCP/UDP,
  `dport`; `proto` = `iph->protocol`. (IPv6 e ingress → futuro; MVP IPv4 egress.)
- Mapa: `BPF_MAP_TYPE_HASH` `flows`, key `struct flow_key {__u32 daddr; __u16 dport; __u8 proto;}`,
  value `struct flow_stat {__u64 bytes; __u64 packets;}`. `bpf_map_update_elem`/lookup+add. Pineable
  (`__uint(pinning, LIBBPF_PIN_BY_NAME)` o pin explícito por bpftool).
- Sin CO-RE: incluye `<linux/bpf.h>`, `<bpf/bpf_helpers.h>`, `<linux/ip.h>`, `<linux/tcp.h>`,
  `<linux/udp.h>`. Compila con `clang -O2 -g -target bpf -c egress_acct.bpf.c -o egress_acct.bpf.o`.

## 4. El gate (`tests/boot/ebpf-egress-and-assert.sh`)

1. Bootea **1 VM** con un machine-config (SMBIOS, patrón 4.1) sobre un perfil estándar + el campo
   `ebpf_egress: true` → `machine-config.sh` setea el flag en runtime.yaml. `-nic user,hostfwd` para
   leer `/v1`.
2. La unidad ata el programa al cgroup de astromeshd y pinea el mapa → assert consola
   `[ebpf] EBPF-EGRESS-ATTACHED OK`.
3. Espera `/v1/health`. POST una corrida al smoke agent `phase0-smoke` (modo stub) → astromeshd hace la
   llamada loopback al stub `127.0.0.1:8081`.
4. Vuelca el mapa `flows`; asserta una entrada para **dst `127.0.0.1:8081`** con **bytes > 0** (o, como
   fallback robusto, una entrada cualquiera con dport=8081/bytes>0) — prueba la contabilidad causal
   por-flujo atribuida al cgroup del runtime. Marker `[ebpf] CAUSAL-EGRESS OK`.
5. `[ebpf] EBPF EGRESS GATE PASSED`.

**Discovery+iterate (§0.1):** si el `cgroup attach` falla por colisión con el filtro de systemd, iterar
el modo de attach (`multi`) o el nivel de cgroup; capturar `bpftool cgroup tree` + `prog list`. Como el
strongSwan de 4.2, la config final comiteada es la que funciona.

## 5. Componentes y aislamiento

- **Programa eBPF:** entrada = skbs de egress del cgroup; salida = mapa `flows`. Contrato = el layout
  del mapa (`flow_key`/`flow_stat`). Testeable aislado (cargar + generar tráfico + dump).
- **Unidad de attach:** entrada = flag runtime.yaml + el `.bpf.o`; salida = programa atado + mapa
  pineado. Guardada. Idempotente.
- **dump:** entrada = mapa pineado; salida = texto. El gate lo consume.
- **machine-config (mod):** cred → flag en runtime.yaml. Reusa el parse PyYAML de 4.1/4.2/4.3.

- Roadmap de Fase 4: 4.4 marcado done (rebanada egress) con referencia de run.

## 7. Riesgos

| Riesgo | Mitigación |
|---|---|
| Colisión con el `cgroup_skb` de systemd (`IPAddressDeny`) en el mismo cgroup | Attach con `BPF_F_ALLOW_MULTI`; discovery+iterate en el gate (nivel de cgroup / modo). El filtro de 3.5 manda en el deny; el nuestro solo contabiliza (retorna allow). |
| `cgroup_skb/egress` no ve loopback / el stub | El hook es a nivel socket → ve loopback; si no, fallback a un destino no-loopback permitido. Confirmar en el gate. |
| El postinst no tiene clang (no compila el `.bpf.o`) | Compilar en host/CI y entregar como build-input `dist/egress_acct.bpf.o` (modelo .deb/otelcol). |
| BTF/CO-RE faltante | El programa es "clásico" (uapi headers, sin vmlinux.h) → no depende de BTF en compile-time; el gate verifica la carga en runtime. |
| Descubrir el cgroup de astromeshd | `systemctl show -p ControlGroup astromeshd.service`; el cgroup ya existe (`After=astromeshd.service`). |
| Cambiar comportamiento de gates previos | Guarda por `spec.ebpf.egress.enabled` (off por default), idéntica a la de 4.2/4.3. |

## 8. Fuera de alcance (futuro)

- **4.4b join por-agente:** el runtime taggea cada socket saliente con un id de agent-run (SO_MARK o
  `bpf_sk_storage`), y el eBPF atribuye el flujo al agente → cierra "por agente" de verdad.
- **4.4b export OTel:** publicar la métrica `flows` (bytes por destino/agente) por el pipeline OTLP de
  4.3 — cierra el círculo de §6.8.
- **4.4b control Rust:** userspace en Rust (libbpf-rs) que reemplaza bpftool y alimenta decisiones de
  control (el "control: Rust" de §12).
- **IPv6 + ingress**, y otras dimensiones (CPU/syscalls) de §12.6.
